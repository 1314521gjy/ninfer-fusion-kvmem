## 2. 真正的机制（三条实测拼起来）

### 2.1 池被"常驻 KV"占满，而且**不因新题面而释放**

上面那条 32k 题面的请求：池前 65024、池后 65024 —— **一个新会话带着 32k 题面进来，池里那 65024 一个 token 都没让**。
（它走的是 host 取回：`prefix_reuse_path: root`、`prefix_cache_hit_tokens: 0`。）

也就是说 65024 是被**留住的常驻 KV**（前缀缓存 / 旧会话检查点 / 锚点），引擎**宁可让新题面走主机，也不腾设备池**。

### 2.2 输出租约是池里**优先级最低**的那份需求

`--kv-lease-growth` 的语义（引擎 `--help` + 启动器注释）：
> reserve a 4096-token output window and extend it **instead of the whole max_tokens budget**; an answer the pool cannot extend ends with `length`

**初始 4096，按需扩**。而空闲只有 **512 token**（65536 − 65024）→ 扩不动 → 冻结在 4096 → 单次回答硬顶 ~4056。
**思维链正是从这 4096 里花**，`reasoning_effort=medium` 下思维链一超，正文就是空 → Hermes 那句「No visible answer was produced」。

### 2.3 引擎**评估过**要不要腾地方，但只给了自己 5 毫秒

同一条请求的 `materialization`（引擎自记）：

```
search_granted_ns          5,000,000     ← 只有 5 ms 搜索预算
search_elapsed_ns          4,906,300     ← 5ms 用光
search_stop_phase          expansion      ← 搜索还在"扩展"阶段就被时间掐断
stop_reason                insufficient_expected_gain   ← 于是判定"收益不足"，放弃
selected_degradation_units 3              ← 确实降级了 3 个单位，仍不够
targets_evaluated          18
```

对照 `--help`：
```
--thorough-admission-search   search up to 250 ms for a new request's reuse plan
                              even while others decode (otherwise 10 ms), ...
```

**默认搜索预算 10ms 量级，实测只拿到 5ms，且停在 expansion 阶段。** 这是一个**不用多花一字节显存**的候选杠杆。

## 3. 所以"为什么不能保 65536 + 不压题面"

因为 **65536 这个池子要同时装两样东西**：

| 要装的东西 | 实测需求 | 备注 |
|---|---|---|
| (a) 你想留住的常驻 KV（长会话的缓存/检查点） | 已顶到 **65 024 / 65 536** | 会话越长越多 |
| (b) 输出租约（思维链要打满，`medium`/`xhigh`） | 需要 **≥16 k** | 初始只有 4 096 |

**65536 只够装 (a)。想装 (b) 就得从 (a) 里挪 —— 而现引擎不肯为"输出"去降级常驻 KV。**
（它只肯为"新题面准入"做腾挪，而且实测连 32k 新题面都没挤动那 65k。）

**这不是"参数没调对"，是池子的容量把两个需求加在一起就不够。** 换句话说：
**"保 65536" ⇔ "池里最多只有 65 k 设备 KV"；"不压题面" ⇔ "常驻 KV 本来就要 ≥65 k"。两条在同一个池子里互斥。**

## 4. 想两个都要：四条路（按"代价从 0 到 +1.7 GiB"排）

### 路 1（代价≈0，最值得先试）：`--thorough-admission-search`
加进 `start-kvmem-8091.cmd`：
```
  --thorough-admission-search ^
```
证据就在 §2.3：搜索是**在 expansion 阶段被 5ms 掐断**的。给它 250ms（50 倍），有机会找到"降级常驻 KV → 换输出租约"的方案。
**不额外吃显存**，只多花准入时最多 0.25s。**未验**。

### 路 2：`--recency-eviction` / `--value-aware-demote`
```
  --recency-eviction ^        rem under pressure give up the least recently used owners first,
                              rem only as many as needed, and demote kept ones to Host
  --value-aware-demote ^      rem prefer evicting the conversations cheapest to rebuild
```
这正是"把常驻 KV 挪去 host、给输出腾设备页"的策略，且 `--host-kv-mib 16384` 已经在。
代价：腾挪时有延迟。**未验**；风险是常驻的可能就是**当前会话自己**，而这两个开关动的是 "owners（会话）"。

### 路 3：换缓存架构 `--use-alt-prefix-caching` + `--host-cache-mib N`
help：`free VRAM becomes block cache and --host-cache-mib sizes the Host tier`、`content-addressed KV blocks and sparse state snapshots`。
即让设备池不再是唯一缓存落点。改动最大，**未验**。

> ⚠️ 路 1–3 若都不成立（有可能），说明"输出让位于常驻 KV"是这份引擎的**既定策略**，只能走下面两条。

### 路 4：把池还给 131072（= `--max-context`，回到原"零超池"设计）
```diff
-  --max-context 131072 --kv-capacity 65536 ^
+  --max-context 131072 --kv-capacity 131072 ^
```
- 你 10-03 自测的代价：整机 **11.5 → 13.2 GiB**，空闲 **4.5 → 2.8 GiB**（+1.7 GiB）。
- 这是唯一"既留住常驻 KV、又有输出空间"的解——因为池终于装得下 (a)+(b)。
- 可选叠加你文档里的原配方：`--default-max-tokens` `16384` → `32768`（`docs\引擎功能速查.md` 第 69 行）。

### 路 5（换端点，不放宽 65536 也不压题面）
其他三个端点的启动器我查过了，**池直接等于上下文，没有"池<上下文"这条约束**：

| 端点 | 启动器里的池设置 | 题面 100k 时剩余输出空间 |
|---|---|---|
| 8081 | `--max-context 111360 --kv-capacity 111360` | ~11 k |
| **8085** | `--max-context 147456 --kv-capacity 147456` | **~47 k** |
| 8080 | llama.cpp（无 pooled-lease 机制） | 另说 |

代价：丢掉 KVMem 那条线的检索特性（以及 131072 这一档本身）。

### 路 6（工程解）：把池做成"档位"
引擎本来就必须串行重启才能换档。做两份启动器：
- **agent/长会话档**：池 131072（full）
- **Blender 让显存档**：池 65536（small，接受长会话下输出会被掐）

### 7.2 统一模型（现在能解释全部观察，含之前两次"推翻"）

设 **额度 = 池 − 常驻**：

1. **常驻随题面增长，直到顶满池。** 会话到 88k–105k 时，常驻直接 65 024（满）。
2. **输出租约只能拿"额度"**，初始 4096，拿不到就以 `length` 收尾。题面 ≥ ~60k ⇒ 额度 ≈ 0 ⇒ 永远停在 ~4056。
3. **能不能真的拿到额度，还取决于引擎肯不肯腾挪**：
   - 池被**别的会话/旧缓存**占着 ⇒ 旗标（250 ms 搜索）能腾出来 ⇒ **合成测试 4056 → 16384 ✅**
   - 池被**本请求自己的长题面**占着 ⇒ 引擎**不降级"当前会话自己"的常驻 KV**（`degradation_units=0` 即证据）⇒ 额度腾不出来 ⇒ **真实负载仍卡 4056 ❌**

这一版模型同时解释了：
- 改前合成（题面 31、池被旧会话占满）卡 4056 —— 是**拿不到额度**（引擎没搜）；
- 改后合成（题面 66、池被旧会话占满）拿到 16384 —— 旗标**腾出了额度**；
- 真实负载（题面 88k–105k）仍卡 4056 —— **额度本身就是 0**，腾也没得腾；
- 10-03 历史（题面 46 610 → 16 384、49 361 → 12 277，**当时还没旗标**）—— 题面只占池的一半，**额度天然存在**。
- 历史（题面 63 174 → 4 081）—— 题面接近池，额度 ≈ 0。

**⇒ 结论：旗标是必要的（它把"能拿却不拿"变成了"能拿就拿"），但不足以突破"额度 = 池 − 题面"这条容量约束。**

### 7.3 这道第二墙怎么破

真实负载要 **题面 ~105k + 思考/正文 ~16k**，那就要求 **池 ≥ 121k+**。所以：

**方案 A（本负载的唯一解）：`--kv-capacity` 65536 → 131072**（与 `--max-context` 对齐，"零超池"）
```diff
-  --max-context 131072 --kv-capacity 65536 ^
+  --max-context 131072 --kv-capacity 131072 ^
```
- 题面 105 380 时剩余额度 ≈ **26k** ≥ 16 384 ⇒ 思考打满也不会空正文；且旗标已在，腾挪能力也具备。
- 代价：显存 +1.7 GiB（整机 **11.5 → 13.2 GiB**，空闲 **4.5 → 2.8 GiB**，10-03 自测）。
- 附带好处：回到"零超池"原设计，同时移除 P0 崩溃的触发前提（池被超池前缀占满）。

**方案 B（保住那 1.7 GiB）：把题面压在 ~46k 以内**（= 池 65536 − 16k 输出额 − 余量）。
- 现在 Hermes `compression.enabled: false`，会话无上限涨到 105k，正好越界。
- 需要开压缩或每轮新会话。

**方案 C：把长会话活换到别的端点**（8081 池=111360 / 8085 池=147456），代价是丢掉 KVMem 这条线的检索特性。

**不建议再堆 `--recency-eviction` / `--value-aware-demote`**：它的 help 明确是 "give up the least recently used **owners**"，
即动的是**别的会话**；本请求自己的常驻 KV 不在其管辖内（这正是 `degradation_units=0` 反映的）。
真想试，只能作为独立变量重启一次验证；预期收益低。
