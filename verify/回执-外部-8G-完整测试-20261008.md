## 4. 功能测试

| 用例 | HTTP | 结果 | 关键数字 |
| --- | --- | --- | --- |
| 短英文对话 `short-en` | 200 | **截断** | `pred_n=32`＝`max_tokens`，`finish=length`（思考占满） |
| 中文对话 `short-zh` | 200 | **截断** | `pred_n=128`＝`max_tokens`，但已给出正确解释（显存带宽） |
| 多轮对话 `multi-turn` | 200 | 通过 | `pred_n=72`，`finish=stop`，答 "Orange, green, purple." |
| 前缀缓存 `prefix-1st` | 200 | — | `prompt_n=2039`，`cache_n=0` |
| 前缀缓存 `prefix-2nd-same` | 200 | **未命中** | `prompt_n=2039`，`cache_n=0`（同 system、不同 user） |
| 前缀缓存 `prefix-3rd-diff` | 200 | — | `prompt_n=1224`，`cache_n=0` |
| 完全相同 prompt 复问 `temp0-run2` | 200 | **命中** | `prompt_n=5`，`cache_n=20` |
| 流式 SSE `sse-count-1to10` | 200 | 通过 | `sse_chunks=17`，`[DONE]=1`，整轮 891 ms |
| `stop=["four"]` | 200 | 生效 | `finish=stop`，输出不含 stop 词 |
| `temperature=0` 两次 | 200 | **确定性** | 两次均为 "Ember & Oak"，`pred_n=221`（跨重启也一致） |
| `seed=42` 两次 / `seed=7` 一次（`temp=0.9 top_p=0.95 top_k=20`） | 200 | **seed 生效** | 42→"The Ember Room"（两次相同，`pred_n=248`）；7→"The Amber Cup"（`pred_n=176`） |
| `seed` 固定（`top_k=40`） | 400 | 测试写错 | `top_k must be in [0,20]` —— 引擎上限 20，与默认一致 |
| `max_tokens=0` | 200 | 合理 | `pred_n=0`，`finish=length` |
| 并发 2 请求（`--max-concurrency 1`） | 200×2 | **串行** | 单请求 2.93 s / 3.05 s，两并发 **5.598 s ≈ 2×**；无 429、无排队失败 |

**结论**：
1. **前缀复用只在「完全相同的历史」上生效**（`cache_n=20`），**共同前缀不命中**（`cache_n=0`）。原因就在启动参数 `--max-shared-prefixes 0`（上游规则）；`--help` 说明该默认值是 `max(max-concurrency, 7)`，且另有 `--auto-prefix-grid` 可在无客户端提示时共享前缀。若要提升多轮/多会话复用率，应恢复默认值。
2. **`--max-concurrency 1` 是硬串行**：第二个请求被准入排队而不是并行/拒绝，显存安全，但并发吞吐等于单请求。
3. 短请求"截断"不是引擎缺陷，而是默认思考模式吃掉了输出预算（见 §7 的思考开关）。

## 6. 性能

| 指标 | 值 | 来源 |
| --- | --- | --- |
| Decode 吞吐（短请求） | 45 ~ 84 tok/s（中位 ~55） | full-test / quality-test |
| Decode 吞吐（长输出 700~1200 token） | 45 ~ 50 tok/s | quality-test |
| 长 prompt prefill（chunk 512） | 20k → 801.6；100k → 521.0 tok/s | bench-prefill |
| 长 prompt prefill（chunk 256） | 20k → 800.0；100k → 510.1 tok/s | bench-prefill |
| 长 prompt prefill（chunk 1024） | 20k → 859.3；100k → 600.8 tok/s（**但池 −17.5%**） | bench-prefill |
| 短 prompt prefill | 797 ~ 861 tok/s | full-test |
| MTP 接受率（累计） | `2650 / 5939 = 44.6%`；重启后 `284 / 640 = 44.4%` | /metrics |
| MTP 每 round 提交 | `4154 / 1505 = 2.76` token/round | /stats |
| **宿主开销** | **51.4 ms/round**（`decode_host_microseconds_per_round = 51411`） | /stats |
| **GPU 等待** | **0.62 ms/round**（`decode_device_wait_microseconds_per_round = 619`） | /stats |
| GPU 占用 | 7,525 / 8,188 MiB，利用率 100%，67 °C，114 W | nvidia-smi |

**最重要的一条**：`host_work` 显示每 decode round 宿主耗时 **51.4 ms**，而 GPU 等待只有 **0.62 ms**；`elapsed_seconds.program_submit = 81.35 s` 占了 81.81 s 总时长的 99.4%。

⇒ 本机的推理瓶颈在**宿主侧（CPU/驱动提交）**，不是 GPU 算力。这也解释了 `--gdn-state-fp16` 之外为何显存换速度的杠杆有限：MTP 把每 round 的 2.76 token 提交出去，才把 18.4 rounds/s 拉到约 50 tok/s。

上下文缓存侧的压力数据（`/stats` → `context_cache`）：`checkpoints_dropped=44`、`private_owners_evicted=22`、`private_owners_degraded=1`、`selections.root=25`、`private_turn_closure=8`、`reused_prompt_tokens=110`、`state_operations.restores=8`。
⇒ 在仅 35 个请求的测试量下就已发生 44 次检查点丢弃 —— 这与长会话后期出现 **HTTP 429**（`context_cache_exhausted_requests_total` 递增）的现象一致，是上下文缓存的放置压力，而非 KV 占满。

### 本文件最重要的单条发现：思考模式可以关掉

同一 prompt、同一 `max_tokens=512`：

| 请求字段 | `pred_n` | 说明 |
| --- | --- | --- |
| （默认） | **62** | 先思考再回答 |

## 8. 长上下文边界（沿用前测数据）

| 长度 | 针位置 | 配置 | 结果 |
| --- | --- | --- | --- |
| 20,000 | 5% | auto | HIT |
| 40,000 | 5% | auto | HIT |
| 65,536 | 5% | `NINFER_KV_RETRIEVE=560` | MISS |
| 100,000 | 5% | auto | HIT |
| 100,000 | 5% | `RETRIEVE=560` | MISS |
| 100,000 | 5% | `RETRIEVE=256 + SCORE_BUDGET=256` | HIT（检索日志 `first=78`，正是针页） |
| 120,000 | 50% | `RETRIEVE=560` | HIT |
| 120,000 | 5% | `RETRIEVE=256 + SCORE_BUDGET=256` | MISS（检索退回 `first=1890` 末尾） |

- 超出池（>38,016）**不报错**：HTTP 200，`context_cache_exhausted_requests_total=0`，`llamacpp:kv_cache_tokens` 封顶约 37.5k。
- 但召回是**概率性的且失败静默**：100k 三次冷启动 2 次 HIT、1 次 MISS；120k 两次 1 次 HIT。
- 检索恢复预算恒为 4~8 页（256~512 token）—— 这是 8 GB 档长上下文可靠性的真正瓶颈。
- 连续长请求后出现 **HTTP 429**（此时 `kv_cache_tokens=64`、processing/deferred 均为 0），重启即恢复。

## 9. 结论与建议

### 可信的结论
1. 引擎在本机**功能完整、错误处理规范、生成质量合格**（质量 12/12，错误 11/11 结构化）。
2. **容量天花板是 38,016 token**，由模型 5.94 GiB 的驻留量决定（作者配方 5.52 GiB 才能到 66,432）。
3. **`--prefill-chunk 512` 是稳妥值**：与 256 同池同速，避开 1024 缩池 17.5% 与破坏打分器的风险。
4. **`--kv-headroom-mib 64`** 是本机能开出最大池的取值；≥ 可用显存（975 MiB）会 FATAL。
5. **性能瓶颈在宿主侧**（51.4 ms/round vs GPU 等待 0.62 ms）。
6. **并发是硬串行**（`--max-concurrency 1`），两个请求耗时 ≈ 2×单请求。
7. **可靠使用上下文 ≈ 38k**；超出后为静默的概率召回。

### 建议（按收益排序）
1. **DSH 侧把 `contextWindow` 调低**：当前 256,000 远大于可靠范围，建议 32,768（留安全余量），避免长会话静默失忆。
2. **长任务改用 `reasoning_effort: "none"`**（或 `--no-thinking`），彻底消除"思考吃满 max_tokens 导致截断"。
3. **恢复 `--max-shared-prefixes` 默认为 7**（或加 `--auto-prefix-grid`），让多轮/多会话真正共享前缀（当前 0 只复用完全相同的历史）。
4. 试 `--prefill-cublas`（或 `--fast-prefill-kernel`）看长 prompt prefill 是否进一步提升 —— 本机未测。
5. 试 `--kv-lease-growth`（`--help` 描述为"预留 4096 token 输出窗口并扩展，而不是整段 max_tokens 预算"），可把 `max_tokens` 预留从池里省出来。
6. 若要突破 38k，方向是 `--disk-kv-path`（磁盘 KV 层）或换 5.52 GiB 的 PTQ1 产物；`--lm-head-q4` 只省约 0.55 GiB。
7. Windows 上可试 `--wddm-evictable-budget`（针对本机宿主提交瓶颈）。

## 10. 未验 / 限制

- **未测**：`--disk-kv-path`、`--use-alt-prefix-caching`、`--structured-output`、`--prefill-cublas`、`--kv-lease-growth`、`--no-thinking`、`--request-log-jsonl`、`--device-profile calibrate`（均为 `--help` 中可用但本次未启用的开关）。
- **未压测**：`--host-kv-mib 16384` 的宿主内存压力（只验证了单请求长 prompt 不崩）。
- **未长时间跑稳定性**：本次测试累计约 40 个请求、6 分钟级；未做小时级长跑（429 累积已在短测中出现）。
- `seed` 固定性已验证（见 §4），`temperature=0` 的确定性跨重启一致。
- 无 `/v1/completions`、embeddings、rerank、WebUI：不是缺陷，但限制了可接入的上游形态。
- `/stats` 中 `throughput_tokens_per_second`（decode 19.96 / prefill 28.26）是**含空闲的累计均值**，不代表瞬时速率，勿直接引用。
