# RTX 5070 Ti 本机实测报告

## kvmem-llama.cpp `v0.18.0-ninfer-rc2` + NInfer-KVMem 引擎

**测试主题**：在本机（RTX 5070 Ti 16 GB）上跑 Qwen3.8-27B 量化模型，验证 **256K 有效上下文**、**多轮工具调用**、**长任务不出错**

**测试日期**：2026-10-08（单日完成：仓库取证 → 下载 → 校验 → 解压 → 挂载测试 → 256K 压测 → 落地接线）

**结论一句话**：**三条验收线全部达标。** 有效上下文实测跑到 **255,973 token**；decode **61.5～117.7 tok/s（均值 79.8）**，远高于 50 门槛；32 轮工具续写 **0 报错、0 历史淘汰、100% 逐轮前缀命中**，9 个跨深度埋针 **9/9 全中**。

## 0. 摘要

### 0.1 三条验收线对照

| 验收线（测试前由用户定义）         | 实测结果                                                                                    | 判定        |
| --------------------- | --------------------------------------------------------------------------------------- | --------- |
| **有效 256K 上下文**       | 最终 prompt **255,973 token**；32 轮工具续写零淘汰；**9 个独立埋针全深度命中（3% → 99%），TTFT 1.35～1.45 s**     | ✅ 达成      |
| **decode ≥ 50 tok/s** | 完整生成轮（输出 ≥500，n=12）**61.5 ～ 118.0，三轮均值 79.5 / 80.0 / 79.8 tok/s**；192K～256K 区段 **82.7** | ✅ 达成，余量很大 |
| **多轮工具 + 长任务不出错**     | 32 轮 **0 报错 / 0 淘汰 / 100% 逐轮前缀命中**；`max_tokens 16,384` 闸门通过                             | ✅ 达成      |

### 0.2 三个非默认开关（缺一不可）

实测证明，厂商配方直接照搬在本机会失败；必须改三处：

1. **`--kv-dtype rk4v4-e8`** —— 厂商配方用 `int8`，同一个 90,112 池在本机**直接起不来**（需 3.42 GiB，只给 2.57 GiB）；换 `rk4v4-e8` 后只要 **2.00 GiB**。
2. **`--kvmem-sink-tokens 10240`** —— 默认 0 时，最早历史（深度 3%）的**首次**取回要 **221.66 秒**；抬到 10,240 后降到 **1.4 秒**。
3. **`--device-profile-path` 指向 RC2 专属路径** —— 否则 RC2 会改写本机既有引擎的设备校准缓存（实测已发生，见 §12.1）。

### 0.3 与厂商官方数据的对比（同程序同负载）

厂商在 **RTX 5060 Ti** 上跑过同规格 256K 压测（官方发布页与包内 `provenance/task2-summary.json`）。

| 指标            | 厂商 RTX 5060 Ti（int8） | **本机 RTX 5070 Ti（rk4v4-e8）** | 比         |
| ------------- | -------------------- | ---------------------------- | --------- |
| 最终输入 tokens   | 261,528              | **255,973**                  | 基本同       |
| 工具轮           | 32                   | 32                           | 同         |
| 加权 decode     | 41.58 tok/s          | **74.6 tok/s**               | **1.8×**  |
| 末轮 decode     | 45.12 tok/s          | **117.7 tok/s**              | **2.6×**  |
| 末轮 TTFT       | 23.61 s              | **3.49 s**                   | **6.8×**  |
| 历史淘汰          | 0 次                  | 0 次                          | 同         |
| 峰值显存          | 15,200 MiB           | **15,205 MiB**               | 同         |
| **系统可用内存最低值** | **524 MiB** ⚠️       | **8,227 MiB**                | **好 15×** |

**⇒ 同一套配方，本机跑得更快、内存压力小一个量级。**

> ⚠️ 口径提醒：两者 KV dtype 不同（厂商 int8 / 本机 rk4v4-e8），速度对比要留这个余地；但内存差距的主因也正是 dtype —— `rk4v4-e8` 的主机侧 KV payload 显著小于 int8。

### 3.3 A 阶段负载构造（复现厂商 `scripts/windows/task2-dual-256k.py` 的逻辑）

```
system + user 初始请求
  ├─ 第 1 轮：追加 assistant.tool_calls(read_file) + tool 结果 → 约 +8k token
  ├─ 第 2 轮：同上（历史累积）
  └─ … 直到 prompt_tokens 逼近 max_context − 512 − 64
```

- 每轮工具结果首行埋唯一标记 `needle=ND-<轮号>-<5位随机值>`，供 B 阶段回问。
- 实测每轮增量**恒定 +8,176 token**（校准成功；末轮 +2,431 收尾）。
- 服务端 `--default-max-tokens 512`，与厂商配方一致。
- 脚本自带 `--min-available-ram-mib 2048` 三重连读保护，触发即自动终止服务。

> ⚠️ 字段映射坑：厂商那份脚本是 llama.cpp 版，读 `usage.prompt_cache_hit_tokens`；  
> **ninfer 返回的是 `prompt_tokens_details.cached_tokens`，必须映射**，否则第 2 轮起会误报"丢失前缀缓存"。

### 3.4 判据口径说明（本报告的数字口径）

- **decode** 一律取**服务端**口径（`req#N done | … decode X tok/s`），不取客户端计时。
- **decode 均值**分两个口径列出，避免混淆：
  - **完整生成轮**（输出 ≥500 token，n=12）：这是有效数字；
  - **全部 32 轮**（含只输出几十 token 的噪声轮）：会被拉低，仅作参考。
- **"有效上下文"**&#x4E0D;只看 token 计数，必须有 **B 阶段埋针**支撑（厂商那次**没做**这项）。

## 5. 测试二：容量探针 —— 厂商配方在本机装不下，必须换 dtype

### 5.1 问题：厂商原配方 `int8 / B+R = 90,112` 直接 FATAL

```
FATAL server failed during startup | requested Engine runtime reservation
      requires 3669703168 bytes, but only 2755764224 bytes are available
```


即：需要 **3.42 GiB**，本机当时只给得出 **2.57 GiB**。

### 5.2 逐档扫描（脚本 `_rc2_capacity_probe.py`）

| dtype        | B+R              | runtime 占用              | 结果       |
| ------------ | ---------------- | ----------------------- | -------- |
| **rk4v4-e8** | **90,112（厂商原样）** | **2.00 GiB（剩 864 MiB）** | ✅ **能起** |
| rk4v4-e8     | 81,920           | 1.86 GiB                | ✅        |
| rk4v4-e8     | 73,728           | 1.71 GiB                | ✅        |
| rk4v4-e8     | 65,536           | 1.57 GiB                | ✅        |
| int8         | 90,112（厂商原样）     | 需要 3.42 GiB             | ❌ 起不来    |
| int8         | 65,536           | 需要 2.66 GiB             | ❌ 起不来    |
| int8         | 53,248           | 2.19 GiB                | ✅        |

**⇒ 同一个 90,112 池：`int8` 要 3.42 GiB，`rk4v4-e8` 只要 2.00 GiB（0.58×）。**  
**⇒ 因此本机全部 256K 测试使用 `rk4v4-e8`。**

> 依据：`rk4v4-e8` 每页（64 token）1.10 MiB，相对 bf16 困惑度仅 **+0.30%**（厂商公开实测），

## 8. 测试五：客户端 max_tokens 闸门

**背景**：本机既有 GSQ 档有一条硬红线 ——「客户端 `max_tokens` 必须 ≤ 4096，超了 worker 崩且 `/v1/models` 仍返 200（假健康）」。  
换引擎后**必须重验**，否则会重演"假健康"。

### 8.1 结果

同一进程内连发（256K 配方 / rk4v4-e8 / B+R = 90,112）：

| max_tokens | completion_tokens | finish | 客户端 decode      | TTFT   | worker 存活 |
| ---------- | ----------------- | ------ | --------------- | ------ | --------- |
| 4,096      | **4,096**         | length | 143.6 tok/s     | 0.32 s | ✅         |
| **16,384** | **16,384**        | length | **165.6 tok/s** | 0.04 s | ✅         |

服务端口径：`output 16,384 | total 1m 39.0s | decode 168.2 tok/s | mtp accepted 12,856/14,108 (91.1%)`

收尾探活：`/v1/models` → **HTTP 200** ⇒ **不是"假健康"**（长生成之后同一进程仍正常应答）。

### 8.2 结论

**⇒ 那条「GSQ 客户端 max_tokens ≤ 4096」的红线只属于旧引擎，不是模型的固有限制。**  
**⇒ 新档 `maxOutputTokens` 可设为 16,384。**

> ⚠️ 保留：本次只判"worker 是否存活 + 是否真产出 16,384 token"，**未判输出内容正确性**。  
> ⚠️ 另注：由于上限是 `输入 + 输出 ≤ 262,144`，**256K 输入与 16,384 输出无法同时拉满**  
> （实测输入 255,973 时输出只能给 512）。

- **后果（实测）**：本机既有引擎读不了也写不回该文件 ⇒ **每次启动要重新校准（51 秒，原来 6.4 秒）且永远存不下来**。

### 12.2 Cherry Studio `order_key` 重复键（本次接线引入，已修）

- **现象**：接入第 3 档时给新 provider 取 `order_key='b0E'`，但该键**已被 ComfyUI 占用**（原判断引用了过时结论）。
- **危险**：Cherry 的 `generateKeyBetween(a, b)` 在 `a >= b` 时抛错 ⇒ 相邻相等键会让"插到两者之间"的操作崩客户端  
  （**与当天 19:02 那次"更新后起不来"属同一类隐患**，那次根因是非法键 `zz`/`zy`）。
- **修复**：事务内改为 `b0F`（改前断言原值、断言新键未占用且合法、提交后断言 rowcount=1），并 `wal_checkpoint(TRUNCATE)`。  
  **全 13 张带 `order_key` 的表按真实规则复扫：非法 0 行 / 重复 0 行。**

### 12.3 教训

1. **改客户端数据库的排序键前，必须现扫当前最大值**，不能引用旧结论。
2. **两套引擎共用用户级缓存路径时，必须显式隔离**（RC2 一律带 `--device-profile-path`）。

### 15.2 术语

| 术语                | 含义                                                                                |
| ----------------- | --------------------------------------------------------------------------------- |
| **B / R**         | `--kvmem-budget`（历史 GPU 常驻预算）/ `--kvmem-gen-reserve`（生成预留）；两者之和 = 设备 KV 池 token 数 |
| **sink / recent** | 设备上**永久保留**的历史头段 / 最近段窗口，保证首尾不被换出                                                 |
| **主机层（Host KV）**  | `--kvmem-host-mib` 指定的主机内存区，存放被换出的历史原始 KV，按查询回灌                                   |
| **KVMem**         | 仓库的核心机制：**有界 GPU KV 工作集 + 主机内存存历史 + 按查询检索回灌**                                     |
| **埋针（needle）**    | 在历史某深度植入唯一标记，之后回问，用于验证"深层信息是否真的可取回"                                               |
| **假健康**           | HTTP 200 但答案错误，或 worker 已崩但 `/v1/models` 仍返 200                                   |
