### 2.2 逐项含义

| 参数 | 含义 | 为什么必须写 |
|---|---|---|
| `-S <src>` / `-B build-89` | 源码目录 / 构建目录（**在源码树之外**） | 源码树保持干净；`build-89` 的名字本身就标明架构 |
| `-G Ninja` | 生成器 | 与 `CMakeCache.txt` 的 `CMAKE_GENERATOR:INTERNAL=Ninja` 一致 |
| `-DCMAKE_BUILD_TYPE=Release` | 单配置生成器的构建类型 | Release 才有 `/O2 /Ob2 /DNDEBUG`（见 §1.1 的 flags） |
| `-DCMAKE_CUDA_ARCHITECTURES=89` | **按卡改的那一个字**（见 2.3） | 决定二进制里带哪些 SASS |
| `-DCMAKE_CUDA_COMPILER=…nvcc.exe` | 显式指定 nvcc（正斜杠） | 本机 CUDA 不是标准安装位置（在 `E:\cuda-13.3`） |

| `-DCMAKE_PREFIX_PATH=…` | 依赖查找前缀 | curl / FFmpeg 从这里来（§1.3） |
| `-DVCPKG_TARGET_TRIPLET=x64-windows` | vcpkg 三元组 | 与 cache 一致 |

## §3 构建

### 3.1 两个脚本，两种用途

| 脚本 | 用途 | 关键动作 | 日志 | 判据 |
|---|---|---|---|---|
| `rebuild-inc.cmd` | **增量**重编（日常改代码） | `ninja -C build-89 -j 16` | `rebuild-inc.log` | `NINJA_EXIT=0` |
| `clean-rebuild.cmd` | **全量**重编（**任何运行期结论之前必须做**） | 先 `del /s /q *.obj` + `*.obj.ddi`，再 `ninja -C build-89 -j 16` | `clean-rebuild.log` | 先 `OBJECTS_LEFT=0`，再 `NINJA_EXIT=0` |

两个脚本都做同一套前置：`vcvars64.bat` → `VSLANG=1033` → `PATH` 前置 CUDA 的 `bin` 与 `bin\x64`。

### 3.2 ⚠️ 判据只有一行：`NINJA_EXIT=`

构建脚本**最后一句是 echo**，所以**进程退出码恒为 0**（坑表 **§5.111**）。唯一可用判据是脚本打印的：

```
NINJA_EXIT=0
BUILD_SCRIPT_DONE
```

> 我们**不**用"解析 ninja 日志里有没有 FAILED"当判据（ninja 失败时确实会打 `FAILED: <目标>`，
> 但那是它的输出形状，不是我们验过的判据）。**要不要通过，看 `NINJA_EXIT=`。**

### 3.3 为什么"运行期结论之前必须全量清干净再编"（**脚本注释里的实测原因**）

`clean-rebuild.cmd` 头部原文要点：

- 该轮的 P4a mask 补丁**改变了分页 KV 元数据结构的布局**（新增 `selected_blocks` 成员）；
- 凡是 include 了那些头文件、却**没有被重编**的翻译单元，就会与其余部分对**布局**的理解不一致 ——
  这类 bug 的已知表现是**运行期在栈守卫处崩溃（`0xC0000409`）**；
- 所以 **"ninja 认为它是最新的" 不是"每个 TU 都同意"的证据**；删掉全部 `.obj` 直接把这个疑问消除。

**成本（同一注释里的实测）**：约 **55–60 分钟**（665 边的全量构建；32 个 `causal_cache` 巨兽 TU，每个 37–40 MB，
是内存/IO 受限，**加 `-j` 不线性**）。

## §4 依赖捕获修复（**全篇最有价值的一节**）

> 这一节记录的是一个**编得出来、跑起来就崩**的故障，以及它真正的载体在哪。
> 代价：一天的排错。收益：知道**判据该打在哪个文件上**。

### 4.1 症状与后果链（一句话：构建说"成功"，运行期堆损坏）

```
CMake 检测到 cl 的本地化消息 → 把它的字节**误解码**后又按 UTF-8 **重编码**
        ⇒ 双重编码乱码被烘进构建规则
        ⇒ ninja 逐字节比对 msvc 前缀 **全部失配**
        ⇒ 每个目标都记成 #deps 0（头文件依赖 = 空）
        ⇒ 改头文件**不再触发**依赖它的 TU 重编
        ⇒ 二进制里新旧 TU 对"分页 KV 元数据结构布局"的理解不一致
        ⇒ 构建"成功"、启动即崩：0xC0000409 / 0xC0000005 / 堆损坏
```

**坏状态的原始记录**（文件 `（本机构建根）\fusion-master\deps-prefix-check.txt` 全文）：

```
msvc_deps_prefix = 娉ㄦ剰: 鍖呭惈鏂囦欢:
```

（那就是"注意: 包含文件:"被双重编码后的形状。）

### 4.2 根因：一个**本地化前缀**被逐字节比较

`cl.exe` 在 `/showIncludes` 下打印的"包含文件"提示是**本地化**的。CMake 把这条消息检测出来当依赖前缀，
ninja 用 `msvc_deps_prefix` **逐字节**剥离它。两端字节不一致 ⇒ 剥离失败 ⇒ `#deps 0`。

**隔离复现的读数**（`patch-prefix.js` 第 3–6 行记录的实测，用 `probe3.cmd` 在**独立的** ninja 小工程里做的，
`build-89` 未被触碰）：

| 前缀字节 | 结果 |
|---|---|
| UTF-8 的 `注意: 包含文件:  ` | `tiny.obj: #deps 1`（捕获成功） |
| 同一句的 **GBK** 字节 | `tiny.obj: #deps 0` |
| CMake 烘进去的**双重编码乱码** | `tiny.obj: #deps 0` |

### 4.3 ⚠️ 判据要打在哪份文件上（**同名不同物，这里是两个变量名**）

这是本节最容易写错、也最容易**误报**的地方：

| 端点 | 文件 | 变量名 | 谁读它 |
|---|---|---|---|
| **CMake 的检测结果**（补丁打这里） | `build-89\CMakeFiles\4.3.1-msvc1\CMakeCCompiler.cmake`<br>`build-89\CMakeFiles\4.3.1-msvc1\CMakeCXXCompiler.cmake` | `set(CMAKE_C_CL_SHOWINCLUDES_PREFIX "…")`<br>`set(CMAKE_CXX_CL_SHOWINCLUDES_PREFIX "…")` | CMake（configure 时） |
| **ninja 真正读的那一行**（**判据打这里**） | `build-89\CMakeFiles\rules.ninja` | `msvc_deps_prefix = …` | ninja（每次构建） |

> **两份文件的变量名不同**：在编译器配置文件里 grep `msvc_deps_prefix` **什么也找不到**。
> 我们（09-30）就据此误判过一次"修复丢了"，当场被实测推翻 —— 记录在坑表 **§5.154**。
> **结论：判据打在 `rules.ninja`，因为那是 ninja 实际读取的那一份。**

**本次实测的两个端点（都是好值）**：

```
rules.ninja     : msvc_deps_prefix = 注意: 包含文件:
                  值字节(UTF-8) = E6B3A8E6848F3A20E58C85E590ABE69687E4BBB63A2020
CMakeCCompiler.cmake    : set(CMAKE_C_CL_SHOWINCLUDES_PREFIX "注意: 包含文件:  ")
                          值字节(UTF-8) = E6 B3 A8 E6 84 8F 3A 20 E5 8C 85 E5 90 AB E6 96 87 E4 BB B6 3A 20 20
CMakeCXXCompiler.cmake  : set(CMAKE_CXX_CL_SHOWINCLUDES_PREFIX "注意: 包含文件:  ")
                          值字节(UTF-8) = 同上
```

### 4.4 修复：`depsfix.cmd`（三步，**不构建**）

脚本头部自述的口径：`PATCHED/match=yes` → `RECONFIGURE_EXIT=0` → `PREFIX_MATCH=yes`。三步是：

| 步 | 做什么 | 读数行 |
|---|---|---|
| `[1/3] patch the detected prefix` | 先把两份编译器配置**备份**到 `（本机构建根）\fusion-master\deps-prefix-backup-20260930\`，再跑 `node patch-prefix.js` | `GOOD_HEX=…`、`PATCHED <file> before_hex=… after_hex=… match=yes` |
| `[2/3] reconfigure` | 用 §2.1 的同一套 cmake 命令重新 configure（**这是让新前缀被烘进 `rules.ninja` 的关键步**） | `RECONFIGURE_EXIT=0` + `reconfigure-deps.log` 里的 `Configuring done` / `Generating done` |
| `[3/3] verify rules.ninja prefix bytes` | `node verifyprefix.js` | `PREFIX_MATCH=yes` / `PREFIX_BYTES=…` / `WANT_BYTES=…` |

`patch-prefix.js` 干的事（第 12–18 行）：把 `GOOD = 注意: 包含文件:  `（**结尾两个空格**）
写进 `set(CMAKE_C(XX)_CL_SHOWINCLUDES_PREFIX "…")` 的匹配组里，并**打印改前/改后 hex 做自证**。
`verifyprefix.js` 干的事（第 4–13 行）：按字节比较 `rules.ninja` 里那一行与
`WANT = e6b3a8e6848f3a20e58c85e590abe69687e4bbb63a2020`，打印 `PREFIX_MATCH=yes|no`。

> 同目录另有两个历史件：`fix-deps-prefix.cmd`（**同名带连字符的版本，脚本头部记录它"从代理 shell 启动失败"，
> 保留但别用**）、`probe-deps-prefix.cmd` / `probe3.cmd`（隔离复现用）。**修完只用 `depsfix.cmd` 这条路径。**

### 4.5 修完怎么验（两条，都能变红）

**① 字节判据**（最便宜）：


```bat
  src/models/CMakeFiles/ninfer_model_loading.dir/qwen3_5/config.cpp.obj
```

### 4.6 不要做什么

**不要用脚本往这类文件里手写这个非 ASCII 前缀。** 它只能由 CMake 检测产生、或由 **node 脚本按字节**写入。
理由：本故障的乱码**形状**正是"把 UTF-8 字节按 GBK 解一次、再按 UTF-8 编回去"——
这是"用会误解码的工具写非 ASCII 值"留下的指纹。相关纪律（脚本必须 ASCII-only、非 ASCII 数据走 UTF-8 数据文件）
见坑表 **§5.146 / §5.149**。

### 5.2 池 = **工作集**，不是"剩余显存"

源码：`src\src\models\qwen3_5\program\planning\startup.cpp:127-143`（函数 `ring_resident_pages`）

```
logical_pages = page_count(capacity)
window_pages  = NINFER_KV_WINDOW > 0 ? NINFER_KV_WINDOW / 64 : logical_pages     # 页 = 64 token
lanes         = concurrency == 0 ? 1 : concurrency
per_lane      = min(window_pages + page_count(prefill_chunk == 0 ? 1 : prefill_chunk), logical_pages)
demand        = per_lane * lanes + kRingPoolSlackPages        # kRingPoolSlackPages = 8
return max(min(demand, logical_pages), lanes)
```

**人话**：`池页数 = 常驻窗口页 + 一个 prefill 块页 + 8 slack`（单车道）。**核验**（本档实测）：

```
128 (窗口 8192 token / 64)  +  16 (一个 prefill 块 1024 token / 64)  +  8 (slack)  =  152
启动日志实测：capacity | KV 9,728 tokens, k8v4, auto | pages 152/152 | runtime 1.46 GiB | free 22.5 GiB
（本档默认 KV 档自 2026-09-30 起为 **k8v4**；fp8 时代的同一行是 `…, fp8, auto | … runtime 1.54 GiB`，仅作历史。）
```

（该分解与包 `判据.txt` §2 的说明一致。）代码注释里写明了**为什么不能按"剩余显存"定池**：
按空闲显存定池，会把整张卡花在**并不需要**的常驻 KV 上 —— 正是这个移植要避免的反面。
生效点：`startup.cpp:1479-1482`（`ring_requested() && inputs.kv_capacity_automatic` ⇒ 用 `ring_resident_pages(...)` 定容量）。
页大小的出处：`src\core\paged_kv_cache.h:19` = `inline constexpr std::int32_t kPagedKVPageSize = 64;`（**页 = 64 token**）。

> ⚠️ **`--prefill-chunk` 直接进池公式**（公式里的 `page_count(prefill_chunk)`）。池很小、提示很长时，
> **用引擎默认块**会撞红：实测 ring + **16 页**池 + 40k 提示，`req#1` 起跑 **0.26 s** 就
> `Paged KV reservation invariant was violated`；同一配置补 `--prefill-chunk 256` 立刻两轮 200 且针命中
> （出处：`WORKLOG-exec.md` S3a2 前后两组对照；坑表 §5.131）。
> **本包档位不受此影响**：它用 `--kv-capacity auto`，池按工作集自动定（152 页 = 128 + 16 + 8），所以不必手给块大小。

## §6 ring（KVMem）**五个开关**：缺一个都会"起得来但答案是错的"

`start-8090.bat` 里内置的五个开关（**原文**）：

```bat
set "NINFER_KV_WINDOW=8192"           REM 常驻窗口（token）——"热"集合
set "NINFER_KV_RETRIEVE=8192"         REM 检索预算（token）：按与问题的相关性打分、按需取回
set "NINFER_HOST_PAGEABLE=1"          REM 允许 KV 页住在主机（pinned）层
set "NINFER_KV_RING=1"                REM 允许 --kv-capacity 低于 --max-context
set "NINFER_KV_REUSE_HOSTBACKED=1"    REM 允许"设备池装不下的复用检查点"从主机层被采纳
```

> 🚨 **最危险的一条（实测 2026-09-30，坑表 §5.143）**：
> **只设 WINDOW + REUSE、漏掉 `NINFER_KV_RETRIEVE`** 时，档**照样启动**、复用率**照样 99.9%**，
> **但长提示中段的答案会错**（40k 提示里放在中段的针变得不可见 —— 因为此时环只保留最近窗口），
> **而且一行错误日志都没有。** 这是"静默质量退化"：状态码 200、复用数字漂亮、答案错。

**自检办法（三条，建议全做）**：

1. 启动日志里必须有 **`[ninfer] reuse host-backed: on`** —— 没这行就是门控没生效（`判据.txt` §2）。
2. 同一会话**两轮针测**：把唯一标记（如 `NINFER-NEEDLE-7731`）放在**长提示的中段**，第二轮追问它；
   期望**逐字答对**。这是唯一能同时覆盖"复用"和"检索"的判据。
3. 期望出现引擎自证行 **`[ninfer] adopt host-backed: frontier=… need=… usable=… host_backed=…`**。

> ⚠️ 判据要认对：**门控关掉时**第二轮**仍是 200**、答案**也可能仍然对**（短提示下），
> **红的是 `cache%` 与 `adopt` 计数**（`cache 0.0%` / `adopt=0`），**不是 HTTP 状态码**（坑表 §5.141）。
> 另外 `publish host-backed:` 是**无条件**行为，**别拿它当"门控是否打开"的判据**（`判据.txt` §5）。

1. **只发 sm_89**：本包不含 sm_86 / sm_120 引擎；其它架构被启动件**直接拒绝**（`start-8090.bat` 的 arch 检查，退出码 5/6）。
2. **单车道**：ring 要求 `--max-concurrency 1`，抬高会被**硬拒**（`startup.cpp:1163`）。
3. **文本已验；视觉未验**：三元 v3 制品自带视觉塔，但本档所有实测臂都是纯文本。
4. **"行空洞 vs 注意力可见性"的逐页 trace 未做**：复用的正确性目前由**针测两轮命中**间接证明。
5. **磁盘层（`--disk-kv-*`）零实测**；`>262144`（原生窗口）**未验**且已裁决不做。
6. **小池解码吞吐 86–150 tok/s**（单跑 **n=1**，未取交替中位数）；池 ≥ 前缀时约 130–150 tok/s。
   （口径小差：`README.md` §5 写 86–148，`判据.txt` §5 写 86–150 —— 两处原文都留着，取区间量级。）
7. **CUDA 12.8 的作用未验**（§1.4）：只有 13.3 的机器能否 configure 成功，我们没试。
8. **非 40 系的构建/标定未验**：我们没在 3090 / 4090 / 5090 / PRO 6000 上编过或跑过本档；
   内置表里有它们的**档**，不等于我们验过它们跑**本档**。
9. **`PROBE_KV_BYTES_PER_TOKEN` 仍是 `UNKNOWN`**：R6（启动日志自报足迹）缺这一项（§5.4）。
10. **并发/多路不在范围**：本档是单车道；多路需求用别的档。
