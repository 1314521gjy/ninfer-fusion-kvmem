# 05 · 已知问题与禁忌（照抄会炸的那几条）

> 这一页只写**我们亲手撞过、且有读数**的。每条后面是"症状 → 真因 → 处方"，可以直接当 checklist 用。
>
> **★ 未解决 / 还没修完 / 老包里还带着的，另见 `06-Bug手册.md`**（本页是"已经吃透、照做就绕开"的；那页是"我们还没修好，给你绕法"的）。

## 1. KV 精度：`swift-qwen38-rco-iq3s.ninfer` 不能配行粒度 KV

- **症状**：`--kv-dtype fp8`（或 `rk8v4` / `int8` 这类**行粒度 absmax** 缩放）下，只输出 **2 个 token** 就 EOS
  （`mtp accepted 2/3`、`dflash2 accepted 0/4`），**MTP 与 DFlash2 两臂各跑两次、四次全崩**；
  同一制品换 `bf16` 或 `k8v4` 立刻正常出满。
- **真因**：该制品的**离群通道**把行粒度缩放打垮（值平面量化误差在这一行被放大）。
- **处方**：这一档固定 **`k8v4`**（K=FP8 行256 + V=NVFP4 组16）或 `bf16`。
  `k8v4` 实测 178.7 tok/s（bf16 口径 149.7），而且更省 KV 字节（0.785 vs 1.008 字节/值）。

## 2. 必须带 `--max-shared-prefixes 0`（否则实例会被打砖）

- **症状**：题面页数 **> 设备池页数**（本包池 = 280 页 = 17,920 token）且**逐字节重发同一条题面**时：
  `ERROR engine | worker crash: active KV snapshot full page is not stable` → 该请求 500 → **此后该实例所有请求 503**。
- **触发矩阵（实测）**：池内题面连发 3 次 ✅安全；超池题面**分叉**（加消息）✅安全；超池题面**逐字节相同重发** ❌必崩。
- **真因（源码级）**：`capture.cpp` 的宿主层扫描**放行**"宿主驻留 + 有当前副本"的页，
  紧接着**共享**发布调 `active_snapshot_shape()`，其谓词（`kv_store.h:1506`）仍要求**每页都在设备上** ⇒ 抛。
  即"两道守卫按不同的页状态假设写"。
- **处方**：`--max-shared-prefixes 0`（关闭共享前缀发布）。**代价**：失去"跨会话共享同一段系统前缀"这条**性能**特性；
  "同一会话每轮不重填"走的是私有通道，实测 80k 题面复用 **100%**、TTFT 195 ms ⇒ 零损失。
  （引擎默认值是 `max(max-concurrency,7)`，**所以必须显式传 0**。）

## 3. ring 的五个开关缺一不可（缺了是**静默答错**，不是启动失败）

- **症状**：只设 `NINFER_KV_WINDOW` + `NINFER_KV_REUSE_HOSTBACKED`：能启动、缓存显示 99.9%，但**长题面答错**
  —— 40k 题面**正中**的针**看不见**（因为 ring 只留最近窗口，没有 RETRIEVE 就把中段搬不回来）。**零错误行**。
- **处方**：五个都设：`NINFER_KV_WINDOW` / `NINFER_KV_RETRIEVE` / `NINFER_KV_RING` / `NINFER_HOST_PAGEABLE` /
  `NINFER_KV_REUSE_HOSTBACKED`；并且 `--kv-capacity` 要 **< `--max-context`** 才进 ring 语义（此时 `--max-concurrency` 必须是 1）。
  自检：启动日志出现 `[ninfer] reuse host-backed: on` + `pinning host KV | 16.0 GiB` + `capacity | … pages 280/4,096`。

## 4. 磁盘层（`--disk-kv-*`）在本构建上**没有收益**

- **实测**：功能是通的（被淘汰的会话会落盘、重启后能按前缀回灌，`prompt_n=19 / cache_n=40,058`），
  **但回灌 40,058 token ≈ 984 MiB 花了 22,925 ms（≈43 MB/s）**，与**全量重填 22,840 ms** 等价 ⇒ 白干。
- **真因**：本构建 `NINFER_DIRECTORSTORAGE=OFF`（没有 DMA 直通，走普通映射读 + CRC + 分页 staging）。
  对照：老引擎的 `--disk-cache`（DirectStorage DMA）曾做到 2.52 s vs 85.42 s —— **那是另一套实现，收益不能搬**。
- **两个读数陷阱**：① `diskvk_*` 文件体积是 **open 期预分配**（= `--disk-kv-gib`），**不是写入量**；
  ② 判"回灌有没有生效"看 **`cache_n`**，**不要看 TTFT**（"生效但慢"会被误判成"没生效"）。
- **处方**：内测阶段**不要开**磁盘层；要用等我们编出带 DirectStorage 的版本。

## 5. 组件缺失的表现：加 `--spec` 会 FATAL，不加则慢 ~4×

- **症状**：`--spec mtp` 起不来：`FATAL server failed during startup | Qwen3.5 config: missing component mtp`（3.5 s 退出）。
- **判据**：探测制品头部 —— 本包三档都是 `mtp 38~40 / dflash 211 / proposal 5` ⇒ **三档都能用 dflash2**。
  反面例子（内测包里**没有**、但你可能见到同族小件）：某些重打包件是 `mtp 0 / dflash 0` ⇒ 只能裸跑，
  实测 **71.9 tok/s**（同题面 PQ2 带 dflash2 是 276.8 ⇒ **慢 3.9×**）。
- **处方**：**先探组件再配 `--spec`**；没有对应组件就不要加，或者别用那个件。

## 6. 若干"看起来像模型问题、其实是配置/仪器"的坑

| 现象 | 真因 | 处方 |
|---|---|---|
| 表里"只答 1 个字符就停" | 可能是**取值/解析**的错，也可能是真退化 | 先看原始响应 JSON 的 `finish_reason` 与 `usage`，再看制品组件 |
| 同题面偶发退化（1~2 次/3 次） | 我们在一份 Q4_K_M 制品上见过（三种 KV 精度都会发生 ⇒ 与 KV 无关，**未定位**） | 该制品**未进本内测包**；遇到就×3 重复判定，别用 n=1 下结论 |
| 引擎"日志不动"以为卡死 | 长 prefill 期间吞吐行按 `--log-stats-interval-ms` 打；读日志时**引擎占着文件**，普通读会抛异常/读空 | 用能共享读的方式读，或先停引擎再读 |
| `--kv-capacity auto` 起不来 | 自动池要按"权重之后还剩多少显存"算，若被别的进程占着就不够 | 先确认没有别的推理服务在占卡，或显式给池值 |

## 7. 一份"最小正确启动"自检清单（建议打印）

1. `自检-引擎与卡匹配.ps1` 报 OK（架构对）
2. `PATH` 指到 `engine\`（与 `engine\x64`）
3. 模型路径**全 ASCII**
4. argv 里有 `--max-shared-prefixes 0`
5. 五个 `NINFER_*` 环境变量全设
6. 启动日志出现 `capacity | KV 17,920 tokens, k8v4` 与 `reuse host-backed: on`
7. `/v1/models` 返回 200 且 `context_window=262144`
8. 发一条真请求，`timings.predicted_per_second` 与 `docs\00-三档口径与读数.md` 同量级
