## 1. 先看这三行（90% 的问题在这三行里）

| 日志行 | 它在说什么 | 正常长相 |
|---|---|---|
| `capacity \| KV … \| pages X/Y \| runtime …` | 池有多大（X=物理池、Y=逻辑上限） | 本档：`pages 152/152 \| runtime 1.54 GiB` |
| `[ninfer] reuse host-backed: on/off` | **复用门控**是否打开 | 本档必须 `on` |
| `req#N done \| … \| cache N (P%)` | **这一问**复用了多少 | 首问 `cache 0 (0.0%)`；同会话续问应 ≈`99.9%` |

## 2. 症状 → 判据 → 处方

### 2.1 起不来（进程立刻退出）

| 症状 | 怎么确认 | 处方 |
|---|---|---|
| 退出码 **`-1073741515`（0xC0000135）** | 双击后窗口一闪、无日志 | **缺 DLL**。本包 `engine\` 已含 CUDA 运行库 3 件（`cublas64_13` / `cublasLt64_13` / `cudart64_13`）；若仍报，装 **VC++ 2015-2022 x64 运行库**（`MSVCP140.dll`/`VCRUNTIME140*.dll`）；或在 `start-8090.bat` 里显式设 `CUDA_BIN` 指向 CUDA 的 `bin` / `bin\x64` |
| 退出码 **5 / 6** | 启动件打印 `[ERROR] this package ships an sm_89 engine only` 或 `could not read the GPU compute capability` | 卡不是 sm_89（40 系）⇒ 换对应架构的包；或 `nvidia-smi` 不可用 ⇒ 设 `NINFER_AGENT_CC=8.9` |
| `FATAL … needs a Host KV tier that can hold every page the Device pool cannot: host_pages=… pool_pages=… logical_pages=…` | 日志逐字见上 | **这是特性不是故障**：按消息抬高 `--host-kv-mib`（见 `03-…调优方案.md` §1 的表）。参考：65536 上下文 ⇒ ≥2048 MiB；262144 ⇒ ≥8192 MiB |
| `FATAL … (KVMem ring) requires --max-concurrency 1` | 日志逐字见上 | 把 `--max-concurrency` 改回 **1**（环只服务一条活跃序列） |
| `unknown argument: --disk-cache` | 日志逐字见上 | 本引擎线**没有**磁盘缓存参数 ⇒ 删掉它 |

### 2.2 跑到一半失败

| 症状 | 怎么确认 | 处方 |
|---|---|---|
| `ERROR worker crash: Paged KV reservation invariant was violated` + `HTTP 500` | 日志逐字见上；前面往往有 `demote-other short: freed=0 want=…` | **本档设计上不该出现**（已由"按工作集定池"+启动守卫+惰性领用封住）。若见：把 `--kv-capacity` 从**显式值**改成 **`auto`**（显式小池 + 默认 prefill 块会撞这条，我们踩过）；并把整份日志（含 `--host-kv-mib` / `--max-context` / `--kv-capacity`）发回 |
| `HTTP 429 server overloaded`（**过载型**；另一种"缓存排不下型"见 **§2.6**） | 日志逐字见上，紧跟 `req#N started` | **不是过载**：引擎在执行期连续 8 次 OOM 后把待处理请求按"过载"拒掉（代码里就是这条错误串）。判据：看 `nvidia-smi` 与本档 `runtime` 是否超了；处方：减小 `--max-context` 或减小池/窗口，或关掉 MTP 试一次 |
| 首问很慢（40k 提示 ≈19–22 秒） | `req#1 done \| … TTFT 19.7s \| prefill 2.05k tok/s` | **正常**（冷 prefill）。若**第二问**也 19–22 秒 ⇒ 见 2.3 |

### 2.3 复用没生效（每轮都在重算）

| 症状 | 怎么确认 | 处方 |
|---|---|---|
| 每问都 `cache 0 (0.0%)`，TTFT 一直是 20 秒级 | 日志里没有 `adopt host-backed:` 行 | ① 门控是否 `on`（§1 第二行）；② **客户端形态**：复用靠"**会话推进**"——第二问要把**上一轮的提问+回答+新问题**一起发（同一 session）；**把同一段全文当"独立单请求"重发，永远是 0%**（这是最常踩的一条）；③ 两问之间是否换了 `--model-id`/端口 |
| 有 `adopt host-backed:` 但 TTFT 仍大 | 看 `adopt` 后面的 `need=` 与 `usable=` | `need` 远大于 `usable` 时，第二轮仍要从主机搬页（本档实测仍是 154 ms 级，不该是 20 秒）；若真是 20 秒级，说明复用没被采纳 ⇒ 回报读数 |

### 2.4 答案不对（最危险：不报错）

| 症状 | 怎么确认 | 处方 |
|---|---|---|
| 长提示**中段**的内容被说成"不存在"；短问答/结尾内容正常 | 只有**针测**能发现：`cache` 与所有日志**全都正常** | **漏了 `NINFER_KV_RETRIEVE`**（检索预算）⇒ 补上（见 `start-8090.bat` 的五件套）。2026-09-30 实测反例：漏它时档照样起、照样复用 99.9%，但中段的针答不出来（坑表 §5.143） |
| 答案逐字变了/重复/早停 | 对比 `判据.txt` 的算术门 | ① **KV 档被换了**：本档默认 **`k8v4`**（2026-09-30 起；之前是 `fp8`）。**"长题面只出 2 个 token 就 EOS、日志里一条错都没有" = 值平面的 scale 粒度太粗** ⇒ `fp8`/`int8`/`rk8v4`/`rk4v4` 会中招，换 **`k8v4`**（或 `nvfp4`）即解；**点名制品、机理与未验项**见 `03-基础部署后的调优方案.md` **§7**；② 是否把 `--max-concurrency` 抬了 |
| **长会话/agent 循环里"每轮只回一行计划、不产出正文"**（引擎**一条报错都没有**） | 答案长度是否恒定在几十字符**且逐字相同**；引擎行里 `thinking N/N` 是否**每轮都打满** | **思考模式的重复惩罚缺失**（官方规格 thinking 通道 `presence_penalty=0.0`）：加 **`--presence-penalty 1.0`**，并把 `--default-thinking-budget` 提到 **4096~8192**（别设到每轮必满）；**监督者必须把"空产出"判为失败**。机理、实测读数与"两种病"的区别见 `03-基础部署后的调优方案.md` **§8** |
| 自选任务反复念**同一句计划**（但仍有产出） | 比对连续两轮的自选条目文本是否相同 | 任务层面的空转：**给循环加新鲜约束**（新需求/新验收项），或直接判"与上一轮相同的计划"为失败（同上 §8 病 B） |

### 2.5 环境类

| 症状 | 怎么确认 | 处方 |
|---|---|---|
| 报 `invalid UTF-8 byte at index 4: 0xD3` 之类 | 日志逐字见上 | **路径必须是纯 ASCII**：把包/模型放到 `（本机构建根）\...` 这类路径下；中文路径会让引擎读写失败（本包目录名刻意用 ASCII 就是这个原因） |
| 首次启动慢 10–50 秒、日志出现 `calibrating routes` | 日志逐字见上 | **一次性校准，不是卡死**：此时**别杀进程**。校准结果会落到 `%LOCALAPPDATA%\ninfer\device-profiles.json` |
| 端口在监听，但请求失败/超时 | `Get-NetTCPConnection -LocalPort 8090 -State Listen` 有结果 | **端口在听 ≠ 可服务**（坑 §5.125）：判就绪只看 `GET /v1/models` 返回 200，或一次真请求成功 |
| 显存不够（加载权重阶段 OOM） | 启动日志停在 `loading weights` | 权重 7.28 GiB + 运行时 1.54 GiB ⇒ 建议 ≥12 GB 卡；可加 `--gdn-state-fp16`（≈ −130 MiB，另一档实测）或改用更小的档 |

### 2.6 `HTTP 429`：**上下文缓存排不下**（"重启才好"的那种）

**先分清两种 429**（长得像，真因完全不同）：

| | 过载型（§2.2） | **缓存排不下型（本节）** |
|---|---|---|
| 触发时机 | 执行期**连续 8 次 OOM** 之后 | **连续长请求/长会话之后**，短请求也可能中 |
| 关键读数 | `nvidia-smi` 显存**接近满**、本档 `runtime` 超了 | 显存**没满**、`/stats` 的 `kv_cache_tokens` 很小（KV 池几乎是空的） |
| 计数器 | 不涨 | **`ninfer:context_cache_exhausted_requests_total` 递增** |
| 恢复方式 | 减负载 | **重启即恢复**（这是它的指纹） |

**判据（怎么确认是"缓存排不下"）**：① `/metrics` 里上面那个计数器在涨；② 出现时显存没满、`kv_cache_tokens` 很小；
③ `/stats` 的 `context_cache` 段里 `checkpoints_dropped` / `private_owners_evicted` / `private_owners_degraded` 在涨（说明缓存一直在被挤）；
④ 重启即好。

**真因（一句话）**：放"复用检查点 / 私有 owner"的**上下文缓存**没有位置了 —— 不是显存不够，也不是引擎过载。
引擎现在的行为是**只拒掉这一个请求、进程不崩**（这是 B01 分类修复的效果，旧版会 worker 崩溃）。

**处方（按顺序试，每条都写了怎么判）**：

| # | 处方 | 怎么验 / 变红 |
|---|---|---|
| 1 | **必须带 `--max-shared-prefixes 0`**（硬处方：不带会在"超池题面 + 逐字节重发"时把实例打砖、此后全 503） | 不带时会出现全 503；带上后不再出现 |
| 2 | 客户端 `max_tokens` **不超过设备池 token 数**（输出租约别占着不放） | 降下来后计数器不再涨 ⇒ 就是这条 |
| 3 | 试 `--context-cache-policy rolling`（让缓存按滚动窗口回收）**〔未验〕** | 计数器照涨 ⇒ 这条无效 |
| 4 | 试把 `--host-state-slots` 从默认 8 加大（给检查点更多落脚处）**〔未验〕** | 看 `checkpoints_dropped` 是否下降 |
| 5 | `--host-kv-mib` / `--host-cache-mib` 配套加大（检查点有地方落） | 同上 |
| 6 | 长会话/长请求密了就**定期重启**（现状兜底） | — |

**引擎侧状态**：这条路径目前**只有"拒绝 + 计数"**，"**先降级（丢自己的检查点 / 降级 owner）再拒绝**"的改动**尚未做**（登记在 `已知问题-初期版本.md` 的外部新报 2）。所以现在只能靠上面的处方绕。
