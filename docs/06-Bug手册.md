## §1 🔴 未解决（我们知道、还没修好 —— 给你绕法）

### 1.1 ★ 超窗口"正中针"静默丢失（**唯一正确性级**）

| 项 | 内容 |
|---|---|
| **症状** | 题面**超过显存池**时，**中段**的内容可能**完全看不见**：模型答得像"没读过那段"，**HTTP 200、`finish_reason=stop`、日志零告警** |
| **确切形态** | 不是"超了就一定错"：**非单调** —— 某些长度必错、相邻长度却对。**单人单次"针测通过"不能推广** |
| **现状** | **未解决**（根因未定位）。我们已确认它落在**宿主层 KV 恢复路径**，但还没定到那一行 ⇒ **别等我们修** |
| **绕法（已验）** | **让池装得下题面**：`--kv-capacity` 对应的 token 数 **≥ 你实际要发的题面 token 数**（此时中段不会离开设备池） |
| **判据** | 把"针"放在题面**正中**，然后把题面长度**按几百 token 步进扫一遍**（不要只测一个长度）；同一段内容换个位置再问一次 |

### 1.2 ★ worker 崩且不自愈（**全 503**，而 `/v1/models` 仍 200）

| 项 | 内容 |
|---|---|
| **症状** | 日志出现 `worker crash: Paged KV reservation invariant was violated` ⇒ **worker 死**，此后**该实例所有请求 503**（我们见到 9 分钟仍不自愈）；**而 `/v1/models` 照样返回 200**（健康检查骗人） |
| **复现** | 测试里 **2/2 复现**、签名逐字相同；**唯一被区分开的变量是客户端 `max_tokens`**（给 `32,000` 崩、给 `64` 活） |
| **现状** | **未解决**；候选修法 `--kv-lease-growth`（**未验**） |
| **绕法** | **客户端 `max_tokens` ≤ 池 token 数**（这条以前文档没写，是我们的缺口）；**健康检查不要只看 `/v1/models`，要真发一次请求** |
| **判据** | 崩之前那条请求的 `max_tokens` 是否 ≫ 池；把 `max_tokens` 压到池以下再跑同一剧本，应不再出现该签名 |

### 1.3 12 GB 卡跑官方快档：**差 105 MB** 就 FATAL（**开关其实就在文件里**）

| 项 | 内容 |
|---|---|
| **症状** | `start-pq2-dflash.bat`（`--kv-capacity 17920` + 常驻 vision）在 12 GB 上启动即 FATAL：<br>`runtime reservation requires 2828169729 bytes, but only 2722996224 bytes are available` |
| **性质** | **档位适配，不是引擎缺陷**（两例：RTX 5070 12G、RTX 3060 12G） |
| **绕法（已验）** | 在**你自己的副本**里加上 `--gdn-state-fp16`（**≈ −130 MiB**，开关本来就在引擎里）⇒ 加上后正常启动，`free 917 MiB` |
| **规矩** | **别改官方 `start-*.bat`** —— **复制成 `start-pq2-dflash-12g.bat`** 再改（见 §1.5） |
| **判据** | 启动日志的 reservation 行不再超；服务起来后 `/v1/models` 200 **且**真请求能出 token |

### 1.4 自检脚本会"**假红**"：12 GB 卡可能被判 FAIL

| 项 | 内容 |
|---|---|
| **症状** | `engine\自检-引擎与卡匹配.ps1` 报显存不达标（`required_gib=12`），但你其实**能跑** |
| **真因** | 该脚本的 VRAM 门槛是**写死的 12**，**不是按你那一档算的** ⇒ 门槛与实际不符时会**误报** |
| **现状** | **未修**（我们已记账，下一版改） |
| **怎么读它** | 它说"不达标"**只代表"没到它写死的那个数"**，**不代表你这一档不能跑**；以**真发一条请求**为准 |
| **红线** | **别因为这条红字去砍窗口/改池**——测试里真的有人被它带偏过 |

### 1.5 `SHA256SUMS.txt` 会把你"吓住"（**它不是禁止修改**）

| 项 | 内容 |
|---|---|
| **症状** | 想调参数，但一改 `start-*.bat` 就与 `SHA256SUMS.txt` 对不上 ⇒ 不敢动 |
| **正解** | 那个对账表 = **我们发布那一刻的快照**，用来证明"**你拿到的和发出去的是同一份**"；**不是"不许你改"** |
| **规矩（照这个做）** | **要改就复制一份**：`start-pq2.bat` → `start-pq2.local.bat`，改副本；**原文件保持逐字节不变**，对账表就永远对得上 |
| **判据** | 改完后 `SHA256SUMS.txt` 仍全绿（说明你没动原件），而你的 `.local.bat` 能起来 |

## §2 🟠 已修 / 新版已带（**老包里可能还带着**）

### 2.1 启动器"认卡失效"（一行 bug，**全卡型**都中过）

| 项 | 内容 |
|---|---|
| **症状** | 好卡被判"架构不支持"：报 `this kit ships engines for 8.6 / 8.9 / 12.0 only`，**退出码 5**；或报"读不到卡"（退出码 3） |
| **真因** | 老版 `engine\pick-engine.bat` 里那行 `for /f ... nvidia-smi --query-gpu=... --format=csv,noheader` **逗号没转义** ⇒ cmd 把它拆成两个参数 ⇒ nvidia-smi 报 "Option noheader is not recognized" ⇒ **那段报错文本被当成 compute capability** |
| **现状** | **新版启动器已修**（改成重定向到临时文件再读）。**老包/已发出去的包仍带这个 bug** |
| **绕法（三种，任一即可）** | ① **换用新版的 `engine\pick-engine.bat`**；<br>② **设环境变量自己报卡**：`set NINFER_AGENT_CC=8.6`（30 系）/ `8.9`（40 系）/ `12.0`（50 系）—— 启动器**先看这个变量**，设了就不去读卡；<br>③ 手工把启动脚本里的 `%ENGINE%` 直接指到 `engine\ninfer-serve-<架构>.exe` |
| **判据** | 启动时应打印两行：`Card : compute capability X.Y` 与 `Engine : ...\ninfer-serve-XX.exe`；**打出的是报错文本 ⇒ 你正踩这个 bug** |

## §3 🟡 不报错，但会让你**判错**（口径陷阱）

| # | 陷阱 | 正解 |
|---|---|---|
| 1 | **decode 速度不写"内容形状 + 输出长度"** | 同一台机、同一引擎：**数数字 320~326 tok/s vs 中文散文 100.2**，差 **3.2×** ⇒ 报/比速度**必须带这两项** |
| 2 | **拿别人的速度数当自己的目标** | 参考值**带卡型与带宽**（例：276.8 tok/s 是 4080S 级 / 717 GB/s；3060 只有 360 GB/s）⇒ 不同卡不可比 |
| 3 | **按公式估"首启校准要多久"** | **别用公式**：校准实测 **82 SM 笔记本 47.3 s > 80 SM 台式 37.3 s**（**打破单调**）⇒ 只按卡型对照 |
| 4 | **客户端 `max_tokens` 给得比池大** | 见 §1.2：**`max_tokens` ≤ 池 token 数** |
| 5 | **用 `/v1/models` 200 当"可服务"** | 打砖/worker 死后它**仍返回 200** ⇒ **判据只能是"真发一条请求"** |
| 6 | **以为 MTP 比 dflash2 快** | **MTP 省的是权重**（7.12 vs 8.16 GiB），**不是时间**：全开档实测 **dflash2 626 tok/s vs MTP 311** |
| 7 | **"省 token" 当成"更准"** | 换简思考的微调档会**掉题**（我们实测 20 题门 19/20 → 16/20）⇒ 按任务选，见单独发的《卡死与循环的防治》§5.5 |
| 8 | **只看 `finish_reason` 就下结论** | 半截/空的判定要**看全文是否闭合**（代码围栏成对、`<svg>` 有闭合），`stop` 也可能是空的 |

## §4 ⛔ 红线（照用会出事 —— 细节在 `05`）

| # | 别做 | 为什么 |
|---|---|---|
| 1 | **就地改包内原文件** | 对账表会失配、也毁了"可追溯"；**一律复制成 `.local` 副本再改** |
| 2 | **不带 `--max-shared-prefixes 0` 起服务** | 超池题面**逐字节重发**时实例会被**打砖**（此后全 503）——见 `05` §2 |
| 3 | **ring 只设两三个开关** | 五开关缺一 ⇒ **静默答错**（缓存显示 99.9% 但中段看不见）——见 `05` §3 |
| 4 | **给 Swift 那一档配"行粒度"KV** | `fp8`/`rk8v4`/`int8` ⇒ **只吐 2 个 token 就结束**（5/5 复现）⇒ 用 `k8v4`/`bf16` |
| 5 | **开 `--disk-kv-*`** | 本构建**没有收益**（回灌 40k token ≈ 22.9 s，与全量重填等价）——见 `05` §4 |
| 6 | **路径带中文** | 原生 exe 读不了：`invalid UTF-8 byte` —— 包与模型都放**纯 ASCII 路径** |
| 7 | **在"池 < 题面"的状态下评估长上下文能力** | 那是 §1.1 的地盘，测出来的错**不归模型** |
| 8 | **拿并发跑 agent** | 本档 ring 语义要求 `--max-concurrency 1` |

## §5 我们**暂时不打算做**的（别等）

1. **磁盘层（`--disk-kv-*`）的收益** —— 要等带 DirectStorage 的构建，本构建没有。
2. **低比特 KV 的全档适配** —— 现在只保证各档**能起、答案对**，不保证每个组合都最优。
3. **并发 > 1 的 ring 语义** —— 当前设计就是单路。
4. **"全族档位横扫"的退化率对比** —— 我们有结论的是"思考/回灌"这根轴，不是每档都扫过。
5. **一个"包治百病"的推荐配置** —— 牌面不同（显存/卡/任务形态），我们只给判据与档位，不给万能配置。

## §6 报回执的格式（**照这个填，我们能立刻定位**）

```
[1] 引擎      : 文件名 + 你手上 SHA256SUMS.txt 里那一行（或文件 sha256）
[2] 卡        : 型号 · compute capability · 显存 GiB · 驱动版本
[3] 档位/模型 : 哪个 .ninfer + 文件大小
[4] 起服务    : 完整 argv（可打码路径）+ 五个 NINFER_* 环境变量
[5] 池与题面  : 启动日志里 `capacity | ... pages / ...tokens` 那行 + 你这次题面的 token 数
[6] 现象      : 一次一条，写清"做了什么 → 期望 → 实际"
[7] 原始响应  : 出问题那次的完整 JSON（至少 finish_reason / usage / 内容前后各 200 字）
[8] 复现      : n 次里错几次（**n≥3**）；"只错一次"要注明
[9] 时间点    : 本地时间 + 是第一次跑还是跑了很多轮之后
```

**两条请求**：① **别只发截图**（截图只能当线索，数字要摘成文本）；② **改了什么就先说**（尤其是你动过 `start-*.bat` / KV 精度 / `max_tokens`）。
