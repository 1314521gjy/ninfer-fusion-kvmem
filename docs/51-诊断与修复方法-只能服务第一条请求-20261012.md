# 51 · 诊断与修复方案：引擎只能服务第一条请求（2026-10-12）

> **本件只给方案，不含任何源码改动。** 现象、复现、已排除项、定位步骤、判据全部在这里，照着做即可。
> **证据等级**：`A` = 本机实测（读数随文）｜`C` = 外部自报，未复现。
> **范围**：只讲**"引擎只能服务第一条请求"这一个缺陷**。其他问题（超池复用、输出额度、工具调用格式等）**不在本件范围内**。

---

## §0 一句话

**引擎起得来、`/health` 通、第一条请求 200；但从第二条起全部 429。这与池大小、与复用、与环、与任何一个配置开关都无关 —— 换一支引擎二进制（同模型、同配方）就是 4/4。问题在引擎代码里。**

---

## §1 现象（`A`，逐字读数）

```
config   = [ninfer] reuse host-backed: on
capacity = KV 66,432 tokens, rk4v4-e8, auto | pages 1,038/1,038
req#1  http=200   0.32s
req#2  http=429   0.01s
req#3  http=429   0.00s
req#4  http=429   0.00s
```

引擎给出的响应体原文：

```json
{"error":{"code":"server_overloaded",
          "message":"context cache exhausted: an idle Engine found no placement"}}
```

**三个特征决定了它不是什么病**：

1. **0.01 秒返回** ⇒ 根本没有进到物化阶段，是在**准入阶段**就被拒
2. **日志里一条 error 都没有** —— `materialize-one FAIL` / `retained-prefix` / `entitlement` / `no free page` 之类**一条都不出现**
3. **进程不动** —— 不崩、不退出、端口还在听

## §3 决定性对照：**单变量 —— 只换那个二进制**（`A`）

同一模型、同一条官方配方、同一套环境变量、同样 4 条请求：

| 引擎二进制 | 结果 |
|---|---|
| **随包件**（`engine-v0.11.0-kvmem-20261003` 线，2026-10-01 构建） | q1/q2/q3/q4 **全 200，`finish_reason=stop`** ⇒ **4/4** ✅ |

⇒ **唯一变量就是这个二进制。是引擎代码的问题，不是配置的问题。**

## §4 还没切开的一格（**未验**）

本机有一支**中间构建**（2026-10-11 23:16），构建戳写着：

```
build engine-v0.11.0-kvmem-20261003-98-g43c39c6-dirty
```

⇒ 它是主线 tip **`43c39c6` + 工作区未提交改动** 编出来的，**正好能把"某一批源码改动"与"其后的一批修复"分开**。

**但它加载不了该模型件**：

```
ERROR startup failed | inspecting artifact | 15.0 ms
FATAL [json.exception.out_of_range.403] key 'identity' not found
```

⇒ 该模型件缺 `identity` 块，而这支构建的 schema 检查要求它（2026-10-01 随包件不要求，所以它跑同一个模型件没问题）。
**⇒ 谁能提供一个带 `identity` 的同族制品，这一格就能补上。**

**顺带否掉一个假设**：既然随包件**拿同一个缺 `identity` 的模型件**也能 4/4 ⇒ **制品缺 `identity` 不是死因**。

## §5 修复方案（怎么定位，怎么走）

### 第 1 步：先让引擎自己说话（零成本，一个环境变量）

```
NINFER_MAT_DEBUG=1
```

它会在候选生成与物化价值门上打印（落点在通用的资源管理器与物化规划器里，**不限于某个模型家族**）。

- **出现 `[candgen]` 行** ⇒ 程序**被问过**、根候选非空 ⇒ 卡在**规划器给不出计划**那一步
- **没有 `[candgen]` 行** ⇒ 卡在更早 —— 在 `inspect_admission` 被调用**之前**（车道状态 / 未结事务 / 缓存开关）

### 第 2 步：按第 1 步的结论分岔

| 若卡在 | 去看什么 |
|---|---|
| 规划器给不出计划 | 资源管理器的 `plan_materialization`：**一个空闲引擎为什么给不出放置** |
| 车道 / 事务 | **启动期或第一条请求留下了什么状态**（惰性车道臂、未结事务都是历史踩过的形状） |
| 准入门本身 | 引擎核心里"空闲引擎找不到放置"的那个兜底分支：**它把一个请求判 `Overloaded` 之后，会不会给引擎留下不可恢复的状态** —— 这是首要怀疑 |

### 第 3 步：判据（**每条都能变红**）

- **绿**：连发 4 条**互不相同**的题面（小 `max_tokens` 即可）⇒ **4/4 全 200**，且日志里 `HTTP 429` 计数 = **0**
- **红**：任何一条 429；或出现 `context cache exhausted: an idle Engine found no placement`
- **负控（反着测一次）**：**故意只发 1 条** ⇒ 必须 200。若 1 条也挂，说明夹具或环境不对，不是本缺陷

---

## §6 未验（不许当结论）

1. **"某一批源码改动" vs "其后一批修复" 谁是原因 —— 未切开**（见 §4，被制品兼容挡住）。
2. `NINFER_MAT_DEBUG` 在本缺陷上**没跑过** —— §5 第 1 步就是要跑的第一步。
3. 本缺陷的**根因落点未定**：只知道它发生在准入阶段（0.01 s、零日志），不知道具体是哪一行。
