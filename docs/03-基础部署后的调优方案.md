## 1. 你要调的就三个数（其余别动）

| 旋钮 | 作用 | 本档默认 | 动了会怎样 |
|---|---|---|---|
| `NINFER_KV_WINDOW` | **常驻窗口**（设备上保留多少 token 的 KV） | 8192 | 调大 → 常驻更多、显存↑、中段内容更容易被看见；调小 → 省显存、更依赖检索 |
| `NINFER_KV_RETRIEVE` | **检索预算**（按与查询的相关度把窗口外的页搬回来多少 token） | 8192 | **调 0 = 只剩最近窗口** ⇒ 长提示中段的内容**看不见且不报错**（见 §5） |
| `--host-kv-mib` | **主机 KV 层**（装"设备池放不下的页"） | 4096 | 太小 ⇒ **启动期直接拒绝**并打印所需页数（这是特性）；太大 ⇒ 白占内存 |

**池是自动的**（`--kv-capacity auto`），你不用手算：

```
设备池页数 = 常驻窗口页数 + 一个 prefill 块页数 + 8（slack）
           = 128          + 16                + 8   = 152 页        ← 本档实测 pages 152/152
（1 页 = 64 token；默认 prefill 块 = 1024 token = 16 页）
```

**主机层要装多少**（引擎会自己核对，不够就拒绝启动）：

```
host 页数 >= 逻辑页数 - 池页数
逻辑页数 = ceil(max-context / 64)
host 页数 ≈ host-kv-mib / 2.06 MiB        ← 实测：64 MiB ⇒ 31 页
```

| `--max-context` | 逻辑页数 | 池（auto） | 主机层至少 | 建议 `--host-kv-mib` |
|---|---|---|---|---|
| 32768 | 512 | 152 | 360 页 ≈ 0.72 GiB | 1024 |
| **65536（本档默认）** | 1024 | 152 | 872 页 ≈ 1.75 GiB | **4096** |
| 131072 | 2048 | 152 | 1896 页 ≈ 3.8 GiB | 4096（偏紧）/ 6144 |
| 262144（原生窗口） | 4096 | 152 | 3944 页 ≈ 7.9 GiB | 8192 |

## 1.5 KV 池与 prefill 分块的显存账（按可用显存配档的方法）

> 本节回答部署期的一个常见问题：**提高 `--kv-capacity` 是否必须同时降低 `--prefill-chunk`**（两者是否争用同一份显存）。
> 结论：**该因果关系不成立**，两个量级相差一个数量级（1.5.1）；处置顺序见 1.5.2；按卡配档的方法与建议见 1.5.3。

### 1.5.1 两个量级

池公式（§1）中，分块只以 `page_count(prefill-chunk)` 的形式占用池页数：

| 项 | 每 256 token | 每 1024 token | 性质 |
|---|---|---|---|
| **分块占用的 KV 页** | **4 页 ≈ 4.4 MiB**（`rk4v4-e8`，1.10 MiB/页） | 16 页 ≈ 17.6 MiB | 常驻，可按公式精确计算 |
| **分块自身的工作区**（一次前向处理 chunk 个 token 的中间张量） | 小 | **大，随 chunk 线性增长** | **临时**，不出现在 `capacity` 行里 |

⇒ **限制小显存卡上分块大小的主因是工作区与整卡余量，不是池。**
**只有"写死 `--kv-capacity` + 大窗口"才会出现两个数值互相挤压**（池必须同时容纳窗口与即将写入的那一块）。

### 1.5.2 处置顺序（按性价比排）

1. **池用 `--kv-capacity auto`**（池 = 窗口 + 块 + 8 页），不要写死。
2. **需要容纳更长的提示时，降低 `NINFER_KV_WINDOW`，而不是降低分块** —— 窗口之外的页由主机层与检索承担（§5 陷阱①）。
3. **降低每页成本**：`rk4v4-e8` 1.10 MiB/页（bf16 为 4.0 MiB，省 72%）、`rk2v4-e8` 0.84 MiB/页（省 79%）；质量代价实测 **+0.30% / +2.14%**（困惑度，读数见 `配方-8GB档-实测支撑-20261008.md`）。
4. **使用主机层**：`NINFER_HOST_PAGEABLE=1` + `NINFER_KV_REUSE_HOSTBACKED=1` + `--host-kv-mib`；容量不足时引擎**拒绝启动并打印所需页数**（特性）。
5. **小显存卡关闭 CUDA Graph**：`--no-cuda-graph`。

分块大小对速度的影响：上游 bench 记录 **`prefill-chunk` 1024→2688 速率持平（not a lever）**；我们的 256 vs 1024 同配置 A/B **未做〔未验〕**。显存紧张时以较小分块换取可启动，是当前口径。

### 1.5.3 按可用显存配档

**方法（用 §1 的池公式）**：
```
可给 KV 的字节 ≈ 卡可用显存 − 权重 − 留白(建议 0.5 GiB)
池页数        ≈ 可给 KV 的字节 / 每页实占
窗口 token    = (池页数 − 块页数 − 8) × 64        块页数 = prefill-chunk / 64
```
**每页实占的锚点〔实测〕**：`rk4v4-e8`，池 **1,038 页 ⇒ runtime 1.32 GiB** ⇒ 约 **1.3 MiB/页**（含开销）。权重按件与开关计：PTQ1 件 **5.52 GiB（不开投机）/ 5.94 GiB（`--spec mtp`）**、v3 件 7.28 GiB。

| 卡可用显存 | 建议窗口 | 建议 KV 精度 | 建议 `--prefill-chunk` | 备注 |
|---|---|---|---|---|
| **≈7.4–7.6 GiB（8 GB 卡）** | **65,536** | `rk4v4-e8` | **256** | **〔实测·本机〕** 池 1,038 页 / runtime 1.32 GiB / 整卡 **6.84 GiB**；完整配方见 `配方-8GB档-实测支撑-20261008.md`（该行为**不开投机**；开 `--spec mtp` 时权重 5.94 GiB，池会被可用显存封顶 —— 外部 8 GB 实测 594 页 / 38,016 token）|
| 10 GB | 65,536（保守）→ 可试 98,304 | `rk4v4-e8` | 256–512 | 〔推算·未验〕先核对 `capacity` 行 |
| 12 GB | 131,072 | `rk4v4-e8` | 512 | 〔推算·未验〕 |
| 16 GB | 131,072–196,608 | `rk4v4-e8`（改 `bf16` 前按页价 ×3.6 重算） | 1024 | 〔推算·未验〕 |
| 24 GB | 262,144（原生窗口） | `bf16` 可行 | 1024 | 〔推算·未验〕 |
| **≥32 GB** | 262,144 常驻 + 池 ≥ 前缀 | `bf16` | 1024 | **〔实测·本机〕** 32 GiB 卡：bf16 池 262,144 + 图开 ⇒ decode **59.6–60.0 tok/s**、prefill 2.03k、TTFT 368 ms |

⚠️ **10/12/16/24 GB 四行是按公式推算，不是我们的读数**（本机只有 40 系 32 GiB 卡与 8 GB 档的实测账）。
**验证方法**：起服务后核对 `capacity | KV …, <dtype>, auto | pages X/Y | runtime Z GiB`，要求 `Z + 权重 ≤ 卡可用显存`；再发一条明显超过窗口的长提示，按 §4 的判据看中段内容是否仍可取回。
**窗口的两条硬约束**：① `NINFER_KV_WINDOW ≤ max-context`；② 主机层满足 `host 页数 ≥ 逻辑页数 − 池页数`（§1 表），否则**启动即拒**。

### 1.5.4 本版两处启动期行为变化（与显存分配无关）

| 变化 | 现象 | 处置 |
|---|---|---|
| **B21 启动守卫** | `NINFER_KV_SINK` 与池不满足 `sink + 4 ≤ pool` 时**拒绝启动**并给三条出路（旧版是"能启动但每个请求 429"） | 这是守卫不是显存不足：调小 sink，或调大池/窗口 |
| **B32 检索预算默认生效** | `NINFER_KV_RETRIEVE` 未设时，超过池的请求会**自动获得检索预算**；启动日志出现 `[ring] budgets: skeleton=… evidence=… recent=… free=…` 四元账 | 保持默认最稳；**显式设为 `0` 会被尊重，随后长提示的中段内容会静默丢失**（§5 陷阱①） |

## 2. 显存 ↔ 延迟：用池大小换

| 池 | 运行时 | 40k 提示第二轮 TTFT | 何时选它 |
|---|---|---|---|
| **152 页（auto，本档默认）** | **1.54 GiB** | **154 ms** | 显存不宽裕；这就是本档的意义 |
| 640 页（显式 `--kv-capacity 40960`） | 2.44 GiB | 118 ms | 显存宽裕、只求最低延迟 |

两档的复用比例相同（`cache 40,068 (99.9%)`）——**池大小影响的是"要不要从主机搬页"，不是"能不能复用"**。

## 4. 改完必须怎么验（**这条最重要**）

**"能起来 + 复用率高"证明不了"答案对"** —— 2026-09-30 实测抓到过一个反例：
漏掉 `NINFER_KV_RETRIEVE` 时，档**照样起、第二轮照样 `cache 99.9%`**，
但长提示中段的针**答不出来**，而且**一条错误日志都没有**（坑表 §5.143）。

所以每次改完旋钮，跑这两条（本包 `判据.txt` §3/§4 有原文）：

1. **可判对门**：`7*5` → 期望 `35`；追问 `+2` → 期望 `37`；
2. **针测两轮**：40k 提示、同一会话追问 → 两轮都要能答出针号（`NINFER-NEEDLE-7731`），并看引擎日志里
   `cache …%`（第二轮应 ≈99.9%）与 `adopt host-backed:` 行。

## 5. 两个"静默变差"的陷阱（不报错，但答案会错）

| 陷阱 | 症状 | 怎么发现 |
|---|---|---|
| 漏 `NINFER_KV_RETRIEVE` | 长提示**中段**的内容"不存在"了（模型会理直气壮地说没有） | 只有针测能发现；`cache` 与日志**全都正常** |

## 7. ⚠️ 点名的兼容性问题：某个微调在"行粒度量化 KV"下会早停（**本档换默认档的原因**）

**点名制品**：`swift-qwen38-rco-iq3s.ninfer`
（Swift-Qwen3.8-27B-RCO-IQ3_S-mtp 转出的 v3 制品，**15,017,456,128 B**；引擎自报 `engine ready | qwen3.8-27b-swift`）

**症状**：`--kv-dtype fp8` / `int8` / `rk8v4` / `rk4v4` + 长题面（≥ 约 430 token）⇒ **只输出 2 个 token 就 EOS**（`finish=stop`），
**日志里一条错误都没有**（不是崩溃、不是 OOM）；换成 `k8v4` / `nvfp4` / `bf16` 则正常出满 128 token。

**机理（已由对照实验定位）**：这几档的**值平面**共用一个"粗粒度 absmax scale"——
fp8 = **整行 256 个值 1 个**（`ops/kv_cache/d256_profile.h` 的 `Fp8E4M3Row256`，`quant_group = 256`）、
int8 = G64、rk 系 = G32；值激活里只要有**离群通道**，同组其余值就被压成 0 或 1 个码点。
**`k8v4` / `nvfp4` 的值平面是 G16**，因此免疫。**键平面无罪**：`k8v4` 的键就是 fp8 那条 row-256 编码。

**排除过的解释**（每条都有对照臂，只改一个变量）：换采样 temperature 0.7（照样崩）· 去掉 `--spec`（照样崩）·
dense 模式不用环（照样崩）· 换成真实非重复长文（照样崩）· 长度阈值夹在 **232 ✅ / 432 ❌**（fp8 与 int8 相同）·
真实问答（1,245 token 上下文，fp8 vs bf16）输出**逐字相同** ⇒ 崩的是脆弱续写，不是通用能力。

**制品 × KV 档位（只列跑过的格子；空 = 未跑）**

| 制品 | fp8 | int8 | rk8v4 | rk4v4 | nvfp4 | **k8v4** | bf16 |
|---|---|---|---|---|---|---|---|
| 本包 `Ternary-Bonsai-2-27B-ninfer-v3` | ✅ | ❌ 早停 | ❌ 早停 | ❌ 早停 | — | ✅ | ✅ |
| GSQ-RCO IQ3_S（`gsq_rco_iq3_s_dflash2_prop.ninfer`） | ✅ | — | — | — | — | ✅ | — |
| Swift Q4_K_M（`swift-qwen38-q4km.ninfer`） | ✅ | — | — | — | — | ✅ | — |
| **Swift-RCO IQ3_S（点名这件）** | ❌ **2 token 早停（复现 5/5）** | ❌ | ❌ | ❌ | ✅ | ✅ | ✅ |

**处方**：① 本档默认档 `fp8` → **`k8v4`**（键仍是 fp8，值走 G16）：四个制品同题面全部通过，且更省显存；
② 以后遇到"换个 KV 精度就吐 EOS"的制品，**先按值平面的 scale 粒度换档**（G16 的 `k8v4` / `nvfp4`），
**不要用"位宽更高 ⇒ 更安全"来推断** —— 实测 8 bit 的 fp8 崩、4 bit 的 nvfp4 正常。

**未验（不许当已验读）**：① `k8v4`/`nvfp4` 的**质量**（perplexity）**未与 fp8 做过对比**，目前只有"能跑通、输出正常"这一级判据；
② 值平面 G≥32 为何打垮这个制品，最后一步（"该制品的值激活里确有离群通道"）是**推断**，**未直接测到**；
③ 能过的两档同时也是唯一两档用 **E4M3 字节做 scale**（其余四档是 FP16 scale）⇒ "组大小"与"scale 表示"这两种解释**用现有档位分不开**；
④ `k8v4`/`nvfp4` 在 **3090（sm86）/5090（sm120）** 上的可用性**未验**（本包只发 sm_89 引擎；旧线曾记载"KV 精度能力随架构变"，那是旧引擎口径）。

## 8. ⚠️ 长会话 / 自主循环的**自旋风险**（拿本档跑 agent、自动优化循环的人必读）

> 2026-09-30 实测：三元制品（与包内同一份字节）· 窗口 16k + 宿主 16 GiB + `k8v4` · 12 轮"自己找优化项"的循环。

**先说清：这是两种不同的病，别混为一谈。**

| 病 | 症状（实测读数） | 触发条件 | 引擎报错 |
|---|---|---|---|
| **A. 宣布了不干活** | 连续 **8 轮**答案只有 **61 字符**（一行 `OPT: …` + 一行 `STATUS: WIP`），**完全不产出文件**；每轮仍烧满 `thinking 1,500/1,500, control 25`；**8 轮答案逐字相同**。而同一时刻它**仍答对项目编号、并准确列出自己做过的 4 个优化** ⇒ **不是忘了，是不干** | **思考开** + **`--default-thinking-budget` 每轮被打满** + `--preserve-thinking` | **0 条**（HTTP 200、`stop token`、零 WARN/ERROR） |
| **B. 计划重复（空转）** | 自选的"下一步优化"**同一句重复 9/11 轮**；但每轮仍照常产出文件 | **任务层面**：环境从不纠正、模型确实没有新点子了 | 0 条 |

**A 为什么会发生（官方规格的缝）**：本引擎**按通道**给默认采样（`models/qwen3_5/frontend/frontend.cpp:658-675`，dense Qwen3.5/3.8）：

| 通道 | temperature | top_p | **presence_penalty** |
|---|---|---|---|
| thinking（思考开） | 1.0 | 0.95 | **0.0** ← **不惩罚重复** |
| non_thinking（思考关） | 0.7 | 0.80 | **1.5** |
| post_thinking（须 `--post-thinking` 才生效） | 0.2 | 0.95 | 0.0 |

这与 Qwen 官方规格一致（思考模式官方就写 0.0，非思考 1.5）。⇒ **思考模式下没有任何机制抑制重复**；一旦模型决定"先宣布计划"，下一轮它又会看到自己那条**未执行的计划**（`--preserve-thinking` 把它留在上下文里）⇒ **固定点**形成。惩罚的实现是"**该 token 只要出现过就一次性扣**"（`ops/kernel/sampling_device.cuh:278-283`，范围 [-2,2]；另有按次数扣的 `frequency_penalty`）。

**上游与社区的结论（2026-09-30 查到，出处齐全）**

1. **官方仓库承认这是未修的已知病**：`QwenLM/Qwen3.8` issue #88（昵称已匿名）。统计 1,400 条输出：**思考被截断 17.4%（hard 题 27.5%）**，截断样本 **84% 重复率 >30%**。状态：**自动标 inactive 后锁定，未修**。
2. **官方 maintainer 的配方**（同 issue 下 MEMBER `hzhwcmhf`）：*"temperature=1.0, top_p=0.95, top_k=20, min_p=0.0, **presence_penalty=1.5**, repetition_penalty=1.0"* ——**本引擎思考通道默认值与它逐字相同，只差 `presence_penalty`（引擎 0.0 / maintainer 1.5）**。
3. **★ 不要回灌推理**：生产级 agent 框架 `NousResearch/hermes-agent` PR #18446 原文：*"**Qwen-on-vLLM and other custom providers forbid re-feeding `reasoning_content` from prior turns（Qwen multi-turn spec）— causes context balloon and thinking-mode death loops**"*（测试注释：*"the model re-thinks its own prior reasoning back at itself（Qwen's documented failure mode）"*）。**这一条直接对应本文病 A 的两个"回灌"动作：服务端 `--preserve-thinking` + 客户端回传 `reasoning_content`**（我们的实验两样都做了）。
4. **惩罚要限定窗口才有效**：`jundot/omlx` PR #961（昵称已匿名）⇒ 惩罚只统计**最近 ~20 个 token**。本引擎的计数是**全序列累积、无窗口**（`sampling.cuh` 每选一个 token 就累加），长会话里几乎每个 token 都"出现过" ⇒ 惩罚被摊平，这与本文 A6 实测"只能打断、不能治愈"一致。
5. 同症状的另一条报告：`barozp/Qwen3.8-27B-Opus-Distill` discussion #1 —— *"**'no prose' constraint-stacking causes a non-converging reasoning loop**：… burns its entire token budget on internal reasoning and emits zero visible output"* ⇒ **题面形状（多条硬约束堆叠）本身也可能是诱因**（未做本地单变量验证）。

**处方（两种运行模式，二选一；★ 本包当前采用模式 A，因为体感优先）**

**★ 模式 A —— 体感优先（当前采用）：回灌推理 + 护栏兜底**
- **怎么做**：客户端把上一轮的 `reasoning_content` 原样回传，服务端加 `--preserve-thinking` ⇒ 复用 **74~99.9%**（含 `private endpoint` ≈99.9% 的亚秒态），第二问起常是**亚秒 ~3.4 s**。
- **前置条件（强制）**：必须配**护栏**（见下面通用第 3 条）。回灌是本档实测**唯一的退化触发器**：同配置基线 **10/19 轮无产物**（最长连续 **11** 轮）；**配了护栏后同一配置 `undelivered_final = 0`**。
- **另需**通用第 2 条（`max_tokens` 与思考预算一起算），否则会出现"有文件但是半截"。
- **代价**：上下文膨胀（每轮把推理也带回去），单轮 token 与 KV 都涨。

**模式 B —— 稳妥优先：不回灌推理**
- **怎么做**：服务端**不加** `--preserve-thinking`，客户端**不**回传 `reasoning_content`。
- **读数**：实测 **10 轮 0 次无产物**（单变量臂 A2）。
- **代价**：复用打折 —— `cache` **81.6~89.8%**（`turn closure`）、TTFT **10.4~14.5 s**（prompt ~7 万），随会话累积逐步收敛（另一臂到第 9 轮出现 99.6% / 272 ms）。

> ⚠️ 两种模式下 `thinking N/N, control 25` 都可能**每轮打满**，但**"预算打满"不是触发器，"回灌推理"才是**——A2 每轮照样打满却 0 退化。

**通用（两种模式都要做）**
1. **给思考模式补上重复惩罚**：`--presence-penalty 1.0`（社区补丁值）或 **1.5**（官方 maintainer 值，配 `temperature 1.0` —— 正好是引擎默认温度）。**别超 1.5**：实现是"对任何出现过的 token 一律扣"，且本引擎**没有惩罚窗口**（社区要求限定最近 ~20 token），值越大越可能伤到**满屏重复标签的 HTML/SVG** 结构。
   ⚠️ **它不是解药（实测 A6）**：同一停滞配置加 `--presence-penalty 1.0` 后，12 轮里**第 4 轮退化 → 5~6 轮自行恢复 → 7~12 轮连续 6 轮退化** ⇒ 惩罚**只能打断固定点、不能治愈**。
2. **`max_tokens` 必须 ≥ 思考预算 + 交付物**：实测 A7（思考 8,192 + 上限 12,000）⇒ **12/12 个产物半截**（无 `</svg>`）。要出完整文件，把上限提到 **16k~20k**。
3. **监督者必须把"没交付"判为失败**（★ **模式 A 的强制项**）：本轮实测里驱动**从不纠正"没给文件"**、每轮照问同一句 ⇒ **环境默认接受了退化输出，等于在强化它**。
   **已实测的护栏形态（2026-09-30，判据命中）**：判五态 —— **`EMPTY`**（正文 < 400 字符，或该给文件时 HTML < 2000 字符）、**`TRUNCATED`**（有 HTML 但**没有 `</svg>`**，文件半截）、**`FIXED_POINT`**（与上一轮**逐字相同**）、**`SAME_PLAN`**（`OPT:` 行与上轮相同）、`OK`；任一非 `OK` 就回一句**点名失败原因**的纠正并要求重做（最多 2 次）。
   在最坏配置（思考 xhigh + 预算 1500 每轮打满 + `--preserve-thinking` + 回灌推理 —— 该配置**基线 10/19 轮退化**）上实测：**10 轮里护栏触发 1 次（第 8 轮 `EMPTY` → 重试 → 成功）、`undelivered_final = 0`**，同配置基线是 **11 次空交付**。
   ⚠️ **别只判"有没有文件"**：A7 的 12 个产物"都有文件"却**全是半截** ⇒ **"有文件" ≠ "文件能用"**，`TRUNCATED` 这一态必须有。

   **★ 接收方要实现什么（本包只给要求，不给实现——请按你自己 agent 平台的形态搬过去改造）**

   | 项 | 要求 |
   |---|---|
   | **放在哪一层** | **客户端 / 网关层**（在每次请求返回之后判、判失败再发一次），**不需要改引擎、不需要改模型** |
   | **判什么** | 五态，缺一不可：`EMPTY`（正文 < 400 字符；或"该给文件"的轮次里 HTML < 2000 字符）· `TRUNCATED`（**有 HTML 但没有 `</svg>`**）· `FIXED_POINT`（与上一轮**逐字相同**）· `SAME_PLAN`（自选计划行与上一轮相同）· `OK` |
   | **判失败做什么** | ① 把这一轮判为**失败**（不要计入进度）；② 回一句**点名失败原因**的纠正消息（"你没给出完整文件 / 文件没闭合 / 与上一轮逐字相同 / 计划与上轮相同"）；③ **重试同一轮**，上限 2 次；④ 仍失败 ⇒ 中止该循环或**降级**（换档/换策略/交人工），**不许当作成功继续往下跑** |
   | **为什么必须在平台层做** | 这类失败在引擎侧**完全没有信号**：HTTP 200、`finish_reason=stop`、日志零 WARN/ERROR；实测最坏配置下**10/19 轮**都是"空交付"而引擎一声不吭 |
   | **验收判据（照这个验）** | 同一剧本、同一配置下 **`undelivered_final = 0`**（未交付轮数归零）；**负控**：把护栏关掉，同一配置必须复现退化（实测：无护栏 **11 次**空交付 → 有护栏 **0 次**） |
   | **成本** | 每次重试 ≈ 一轮算力（实测 1 次重试约 2 分钟）；**触发率很低**（实测 10 轮触发 1 次） |
4. **要避免"计划重复"（病 B）**：给循环**加新鲜约束**（新需求/新验收项），或直接判"与上一轮相同的自选计划"为失败。实测这一病**两种模式都躲不掉**（思考关时也出现同一句 ×9 / 11 轮）。
5. **已排除**：投机解码（MTP draft 2）**不是**成因——停滞那场用的就是 MTP、draft=2 是最保守档，且"逐字相同的固定点"不是数值翻转能解释的。
