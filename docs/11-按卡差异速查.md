## 1. 一句话（精确版）

**我们的自适应档位是按"大卡档位"建模的** —— 内置档位表逐字只有 **3090 / 4090 / 5090 / RTX PRO 6000** 四类（共 7 条，见 §2），
**没有** 3060 / 3070 / 3080 这种逐型号条目；成本模型那一套更少，只有 **5090 / 3090 / PRO 6000** 三档。

⇒ **同档位的卡（含未单独列出的型号）在我们的引擎上"天生能跑"，并接近该档的性能水平**；
若要**压到这块卡的极限**，还要做两件事（§4）。

> **【口径】"各显卡天生能跑出约 80% 的性能，剩下 20% 要调内核与引擎"** —— 这是产品口径。
> **【证据状态】**：机制面成立（§2 的档位表与回落规则是逐字核过的）；**但"80%"这个数字我们没有逐卡 A/B 证据** ——
> 我们**只在本机 RTX 4080 SUPER 上有实测**（§3）。⇒ 引用时请按"口径"读，**不要写成"实测 80%"**。

| 档位（hardware_class） | 架构 | 典型卡 |
|---|---|---|

| `nvidia-geforce-rtx-4090-sm89` | sm_89 | RTX 4090（40 系档） |
| `nvidia-geforce-rtx-5090-sm120` | sm_120 | RTX 5090（50 系档） |

| `nvidia-rtx-pro-6000-blackwell-max-q-workstation-edition-sm120` | sm_120 | RTX PRO 6000 Max-Q |

**回落规则（【实测】）**：档位按 **硬件类 + SM 数** 匹配；本机没有的型号会落到最近的档位，
或在**启动期自动校准**（日志出现 `calibrating routes`，一次性、约 10–50 秒）——**这不是卡死，别在此时杀进程**。

**成本模型（第二套自适应面）只内置三档**：`5090-sm120` / `3090-sm86` / `PRO 6000-sm120`
（27B 的 prefill 成本常量以 **sm86** 档为基线，多个签名共用它）⇒ 这正是"用大卡档位方案、不逐卡精细建模"的实证。
⚠️ 该表里**没有 4090、也没有 4080 SUPER**（【实测】逐行核过）。

## 3. 本机实测（RTX 4080 SUPER，sm_89，80 SM）

| 阶段 | 读数 |
|---|---|
| 首次运行（未标定） | 启动日志出现 `calibrating routes`（一次性 10–50 s），随后以校准档运行 |
| 标定并"烘进内置表"之后 | `device profile nvidia-geforce-rtx-4080-super-sm89: 49 routed keys (built in: RTX 4080 SUPER (80 SMs), calibrated on this machine …)` |
| 负控（判据能变红） | 把外部档**移走**后必须命中**内置**档：日志只出现 `device profile …: 49 routed keys`，**不得出现 `calibrating routes`**（脚本 `verify-builtin-4080s.ps1`，读数 `MATCHED_LINES=1`） |
| 本档在 4080 SUPER 上的读数 | 权重 7.28 GiB · 运行时 **1.54 GiB**（池 152 页）· 40k 提示第二轮复用 **99.9% / TTFT 154 ms** |

## 4. 想要那"剩下的性能"：两步（【口径】+【未验】）

1. **按卡校准并烘档**（便宜、一次性）
   - 让引擎在启动期自动校准（日志 `calibrating routes`），标定结果落在
     `%LOCALAPPDATA%\ninfer\device-profiles.json`；
   - 想"内置化"（换机器也不再校准）：把该校准档并进
     `src\runtime\engine\device_profiles.json`（**改这个 JSON 必须重新 configure**，因为它是 configure 期烘进生成源码的）；
   - **判据**：启动日志出现该卡的 `device profile …: N routed keys (built in: …)`，且**不再出现 `calibrating routes``。
2. **内核/调度针对性调优**（另一个量级）
   - 例：三元 GEMM 的档位阈值、prefill 分块与 tile 形状、KV dtype 与架构的搭配等；
   - 本档**不做**，也**未评估收益**。

## 5. 架构与"本包能不能跑"

| 架构 | 卡 | 本包（ring-reuse-8090） | KV dtype |
|---|---|---|---|
| sm_86 | RTX 30 系（3090 档） | ❌ **本包只含 sm_89 引擎**，启动件会直接拒绝 | — |
| **sm_89** | **RTX 40 系**（4090 档；4080 SUPER 已标定） | ✅ 本档目标卡 | **k8v4**（本档默认，2026-09-30 起；之前是 fp8） |
| sm_120 | RTX 50 系（5090 档）/ RTX PRO 6000 | ❌ 本包不含 sm_120 引擎（既有别的包里有先例：`ninfer-serve-sm120.exe`） | — |

**为什么本档用 `k8v4`（【实测】）**：`k8v4` = **键＝fp8 的 row-256 编码 ＋ 值＝NVFP4 G16 分组**。
四个制品在同题面下全部通过（三元 PQ2 · GSQ-RCO IQ3_S · Swift Q4_K_M · **Swift-RCO IQ3_S**），
本档出厂形状实测：针测两轮 PASS、第二轮 `cache 40,059 (99.9%)`、TTFT **142 ms**、运行时 **1.46 GiB**；
KV 每值字节数 1.008 → **0.785**（比 fp8 更省显存）。

*历史（旧读数，保留不改）*：本制品（Ternary Bonsai 2 27B v3）在 `rk4v4` / `int8` / `rk8v4` 上会**早停**（输出仅 4 token、
decode 约 87 tok/s），而 `fp8` 与 `bf16` 速度相当且答案正确 ⇒ 当时把 `--kv-dtype fp8` 写死。
**2026-09-30 换档的原因**：fp8 的**值平面是整行 256 一个 scale**，在值激活带离群通道的微调上会早停
（点名制品：`swift-qwen38-rco-iq3s.ninfer`；机理、对照实验与未验项见 `03-基础部署后的调优方案.md` **§7**）。
⚠️ 别的档位里"按架构自动换 KV 档"（sm_89→`rk4v4`、sm_120→`nvfp4`）是**那些包的口径**，**不要照用到本档**；
**KV 档位的可用性随架构变**（旧引擎线曾记载 sm_89 无 `nvfp4`/`k8v4`、sm_120 反过来）⇒
**能力表要落到按卡表里，别靠默认配置赌**；本包只发 sm_89 引擎，本机（sm_89）上 `bf16`/`fp8`/`int8`/`rk8v4`/`rk4v4`/`nvfp4`/`k8v4` **逐档都真跑过**。

## 6. 显存速查

| 项 | 本档实测 | 说明 |
|---|---|---|
| 权重 | 7.28 GiB | 三元 v3 制品 |
| 运行时（KV 池 + 工作区） | **1.54 GiB**（池 152 页） | 池 = 常驻窗口 128 页 + prefill 块 16 页 + slack 8 页 |
| 主机 KV 层 | **4.00 GiB**（`--host-kv-mib 4096`） | 装"设备池放不下的页"；见 `03-基础部署后的调优方案.md` 的公式 |
| 对照：池 = 前缀（640 页） | 2.44 GiB | 显存换一点延迟：TTFT 154 ms → 118 ms |
| 可再压 | `--gdn-state-fp16` ⇒ 运行时 1.13 → 0.99 GiB（≈ −130 MiB，另一档位实测） | 本档未开 |

**一句话**：本档是给"显存不宽裕、但要长上下文、且多轮对话不想每轮重算"的卡用的；
如果你有 32 GB 显存且只求最低延迟，用大池档（池 ≥ 前缀）更合适。
